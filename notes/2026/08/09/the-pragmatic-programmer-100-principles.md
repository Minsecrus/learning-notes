# The Pragmatic Programmer 100 条原则

1. 认真打磨自己的专业能力。
2. 思考你的工作。
3. 你拥有主动权。
4. 提供可选方案，别拿蹩脚借口搪塞。
5. 不要容忍已经存在的缺陷、糟糕设计和错误决定。
6. 主动推动有益的改变发生。
7. 持续关注系统的整体目标和影响。
8. 把质量作为明确的需求来讨论。
9. 持续投资你的知识和技能。
10. 批判性地分析你读到和听到的内容。
11. 像编写代码一样清晰、简洁、可维护地使用自然语言。
12. 你说什么重要，你怎么说同样重要。
13. 把文档直接构建到系统和工作流中。
14. 好设计比坏设计更容易修改。
15. DRY——避免重复表达同一份知识。
16. 让复用变得容易。
17. 消除无关事物之间的影响。
18. 尽量保留调整和撤销决策的空间。
19. 根据实际问题和证据选择技术，避免盲目追逐潮流。
20. 尽早构建可运行的局部方案，用实际结果验证方向。
21. 用原型验证理解、需求和技术方案。
22. 让程序贴近真实业务和问题背景。
23. 用估算提前暴露不确定性和风险。
24. 根据代码验证结果持续调整进度计划。
25. 用纯文本保存知识。
26. 用命令 Shell 组合和自动化工作流程。
27. 熟练掌握编辑器，让编辑操作高效而自然。
28. 始终使用版本控制。
29. 修复问题，别追究责任。
30. 保持冷静。
31. 先写一个会失败的测试，再修复代码。
32. 仔细读懂错误消息。
33. 先检查查询、数据和假设，别急着认为 select 出错。
34. 别想当然，用证据验证。
35. 学一门文本处理语言。
36. 承认软件不可能完美，持续改进它。
37. 用明确的前置条件、后置条件和不变量设计代码。
38. 尽早发现严重错误并停止执行，避免继续产生错误结果。
39. 用断言检查不变量，尽早捕获不应发生的状态。
40. 完成已经开始的工作，或明确结束它的方式。
41. 把变化和影响限制在局部范围内。
42. 每次只做小幅、可验证的改动。
43. 不要假设未来需求和技术会怎样，依据当前证据做可调整的决策。
44. 减少模块之间的依赖，让代码更容易修改。
45. 让对象直接执行操作，通过行为接口协作，减少对内部状态的询问。
46. 避免让方法调用形成过长的链条。
47. 避免全局数据。
48. 通过 API 管理需要全局共享的重要资源。
49. 编程要写代码，但程序最终处理的是数据。
50. 减少状态的集中持有，让状态沿数据流传递。
51. 警惕继承带来的耦合和维护成本。
52. 优先用接口表达不同实现之间的多态关系。
53. 优先通过服务委托和组合复用功能，减少对继承的依赖。
54. 用 mixin 共享可复用功能。
55. 让应用通过外部配置适配不同环境。
56. 分析工作流，找出可以并发执行的部分。
57. 尽量避免共享可变状态，因为它容易导致不一致和并发错误。
58. 随机失败往往是并发问题。
59. 使用 Actor 模型，在无共享状态的条件下实现并发。
60. 用共享的信息空间协调工作流。
61. 识别并管理面对风险和批评时的本能防御反应。
62. 不要依赖碰巧成立的行为、顺序或环境来编程。
63. 估算算法随输入规模增长的资源消耗。
64. 用实际测试检验对算法性能的估算。
65. 尽早重构，持续重构。
66. 测试用于验证行为、保护回归，并发现 Bug。
67. 先用测试验证代码的使用方式和接口。
68. 先构建贯穿完整流程的可运行方案，再逐步扩展。
69. 为可测试性而设计。
70. 测试你的软件，避免把缺陷暴露给用户。
71. 用基于属性的测试验证对系统行为的假设。
72. 保持简单，减少可被攻击的入口。
73. 快速应用安全补丁。
74. 选择清晰准确的名称，需要时及时重命名。
75. 承认需求一开始通常并不明确。
76. 帮助用户把模糊需求说清楚。
77. 通过反复收集反馈和调整实现来逐步明确需求。
78. 和用户一起工作，站在用户角度思考。
79. 把变化频繁的策略作为可配置的元数据管理。
80. 建立并使用统一的项目术语表。
81. 先识别问题和约束边界，再寻找突破方式。
82. 通过结对编程、代码评审或团队协作来编写代码。
83. 把敏捷落实为持续反馈、快速交付和持续改进的做事方式。
84. 保持团队规模小而稳定。
85. 把重要的改进和学习安排进日程，才能落实。
86. 组建能够独立完成端到端工作的团队。
87. 根据实际效果做事，别追逐时髦。
88. 在用户真正需要时交付价值。
89. 让版本控制触发构建、测试和发布。
90. 尽早测试、频繁测试，并自动执行测试。
91. 所有测试跑完，编码才算完成。
92. 用故意制造错误的测试程序检验测试。
93. 以状态覆盖率检验测试，别只看代码覆盖率。
94. 每个已发现的 Bug 都要用自动化测试固定下来，避免再次出现。
95. 把手工流程自动化。
96. 让用户获得满意和惊喜，交付可用价值。
97. 为自己的成果署名并承担责任。
98. 优先确保软件不造成伤害。
99. 不要为恶意使用者提供便利。
100. 分享成果，庆祝进展，持续改进和建设。
