# 第6章 第一次抓包

## 从一份“报文很多”的界面提出问题

Wireshark 启动后，屏幕上可能迅速出现 DNS、局域网发现、浏览器连接和系统后台流量。我们的程序只交换一句“你好，TCP”，依然会产生连接建立、数据确认与连接关闭等多组 TCP 报文。

本章的目标是从这些流量中准确找到第5章程序，并建立一条从代码到报文的时间线。开始前先预测：

- 服务端执行 `listen` 时，线上会立刻出现 TCP 报文吗？
- 客户端 `connect` 返回前，抓包中会出现哪些标志位？
- 客户端一次 `sendall(16 bytes)`，抓包中一定只有一个携带16字节数据的 TCP 报文段吗？
- 程序结束时，关闭过程会固定产生多少个报文吗？

这些预测会在抓包中逐项验证。

## 抓包点决定你能看到什么

本篇使用 `127.0.0.1`。数据在本机 TCP/IP 栈内部经过回环路径，流量会留在本机协议栈中。Windows 安装 Npcap 后，Wireshark 通常会显示名称类似 **Adapter for loopback traffic capture** 的接口，描述中也可能出现 **Npcap Loopback Adapter**。

抓取这个接口，才能看到 `127.0.0.1` 两端的 TCP 报文。若你把程序改为两台电脑之间通信，则应选择实际承载流量的 Wi-Fi 或以太网接口，并在两端防火墙允许的受控环境内实验。

抓包文件包含程序交换的明文字节。本实验只使用固定测试文本，让账号、令牌和个人数据始终远离抓包文件。

## 捕获过滤器与显示过滤器

Wireshark 有两类过滤器：

- **捕获过滤器**在数据进入抓包文件前筛选，语法来自 BPF。只保留实验端口可以写 `tcp port 50007`。
- **显示过滤器**在已经捕获的数据上筛选，语法使用 Wireshark 字段名。筛选实验端口可以写 `tcp.port == 50007`。

初次实验建议保留完整回环抓包，再用显示过滤器逐步缩小范围。这样即使过滤条件写得过窄，原始数据仍可重新分析。回环背景流量很多时，可以在开始捕获前设置 `tcp port 50007`。

## 完整实验步骤

### 第一步：确认端口当前空闲

在 PowerShell 中运行：

```powershell
Get-NetTCPConnection -LocalPort 50007 -State Listen -ErrorAction SilentlyContinue
```

空输出表示当前没有 TCP 监听 Socket 使用该端口；端口能否成功绑定最终以服务端 `bind` 的结果为准。若有其他程序监听该端口，请在 `server.py` 和 `client.py` 中同步选择另一个端口，并同步调整过滤器。

### 第二步：启动 Wireshark 捕获

1. 打开 Wireshark。
2. 找到回环捕获接口。
3. 双击接口开始捕获。
4. 确认捕获已经开始；回环接口安静时，数据包计数可以暂时保持不变。

### 第三步：运行服务端与客户端

先在一个 PowerShell 中启动第5章的服务端：

```powershell
python -X utf8 .\server.py
```

再在另一个 PowerShell 中启动客户端：

```powershell
python -X utf8 .\client.py
```

等待双方输出完成。记录服务端日志中的 `accept()` 时间、客户端日志中的 `connect()` 时间，以及客户端临时端口。

### 第四步：停止捕获并筛选端口

回到 Wireshark，点击红色停止按钮。在显示过滤器栏输入：

```text
tcp.port == 50007
```

应用过滤器后，列表应集中显示本次实验连接。若你重复运行过程序，可能看到多条使用不同客户端临时端口的连接。

### 第五步：锁定唯一 TCP 流

选中一条属于本次运行的报文，展开中间窗格的 **Transmission Control Protocol**，找到 **Stream index**。假设值为 `3`，继续使用：

```text
tcp.stream == 3
```

`tcp.stream` 是 Wireshark 在当前抓包文件中分配的会话编号，只服务于这份抓包。它让后续分析始终聚焦同一条双向连接。

还可以右键选中的报文，选择 **Follow → TCP Stream**。窗口会按方向着色展示 Wireshark 重组后的字节流。前4字节是二进制长度字段，显示为不可打印字符；其十六进制值应为 `00 00 00 0c`，后面12字节是“你好，TCP”的 UTF-8 编码。两个方向各有一份相同应用帧。

Follow TCP Stream 展示的是分析器重组结果。颜色表达方向，应用消息边界来自本程序的4字节长度字段。

## 先认识关键字段

选中任意 TCP 报文，Wireshark 会显示：

- **Source / Destination**：当前报文的源 IP 与目标 IP；
- **Src Port / Dst Port**：当前报文的源端口与目标端口；
- **Flags**：SYN、ACK、FIN、RST 等控制位；
- **Seq / Ack**：序列号与确认号，本章采用 Wireshark 默认的相对值；
- **Len** 或 `tcp.len`：该 TCP 报文段承载的 TCP 数据字节数；
- **Stream index**：Wireshark 对该连接的本地编号。

Wireshark 默认把初始序列号换算成容易阅读的相对值，所以首个 SYN 常显示 `Seq=0`，SYN+ACK 常显示 `Seq=0, Ack=1`。线上首部携带的是32位实际序列号；第10章会计算两种显示的关系。

## 一条典型时间线

本地回环、无丢包的一次运行常见以下顺序。`C` 表示客户端，`S` 表示服务端：

| 方向 | 常见标志 | `tcp.len` | 当前意义 |
| --- | --- | ---: | --- |
| C → S | SYN | 0 | 客户端发起连接 |
| S → C | SYN, ACK | 0 | 服务端确认并给出自己的连接信息 |
| C → S | ACK | 0 | 客户端完成握手方向的确认 |
| C → S | PSH, ACK 或 ACK | 16 | 4字节长度字段与12字节请求体 |
| S → C | ACK | 0 | 服务端 TCP 确认请求字节，可能与响应合并 |
| S → C | PSH, ACK 或 ACK | 16 | 服务端回显同一应用帧 |
| C → S | ACK | 0 | 客户端 TCP 确认响应字节，可能与关闭报文合并 |
| 双向 | FIN, ACK 与 ACK 的组合 | 0 | 两个发送方向依次结束 |

这张表是一种常见观察结果。TCP 允许确认与数据合并，最终握手 ACK 也可以携带数据；FIN 可以和 ACK 或数据出现在同一报文段。操作系统调度、确认策略、发送时机和卸载功能都会影响列表的具体行数。

第5章客户端把16字节帧一次交给 `sendall`。在回环实验里，它常常显示为一个16字节 TCP 报文段。协议仍允许它被拆成多个报文段；接收端 `recv_exact` 对任何分段方式都适用。

## 用过滤器回答具体问题

先把 `N` 替换为实际流编号。

### 找握手相关报文

```text
tcp.stream == N && tcp.flags.syn == 1
```

只看最初由客户端发出的 SYN：

```text
tcp.stream == N && tcp.flags.syn == 1 && tcp.flags.ack == 0
```

### 找携带应用数据的报文

```text
tcp.stream == N && tcp.len > 0
```

选择客户端方向的16字节报文，在下方 **TCP payload** 或 **Data** 区域可以看到长度字段与 UTF-8 字节。若数据分成多段，各段 `tcp.len` 之和仍对应完整帧长度。

### 找正常关闭与重置

```text
tcp.stream == N && tcp.flags.fin == 1
```

```text
tcp.stream == N && tcp.flags.reset == 1
```

本程序正常完成时通常能看到双方 FIN，RST 过滤器通常为空。RST 的场景将在第19章专门实验。

### 找分析器推断的重传

```text
tcp.stream == N && tcp.analysis.retransmission
```

稳定回环实验的过滤结果通常为空。`tcp.analysis.retransmission` 属于 Wireshark 根据当前抓包上下文给出的分析标记。抓包从连接中途开始、抓包点丢包或卸载行为都可能影响推断，因此诊断时要把它与序列号、时间间隔和其他证据共同使用。

## 把 API 日志与报文对齐

程序日志记录用户态调用前后的时间，Wireshark 时间戳记录报文经过捕获点的时间。它们观察的是相邻层次，适合建立下面的对应关系：

| 程序事件 | 抓包中的对应现象 | 证据层次 |
| --- | --- | --- |
| 服务端 `listen` 返回 | 抓包列表通常保持原样 | Socket API 与操作系统状态 |
| 客户端进入并完成 `connect` | SYN、SYN+ACK、ACK | API 与 TCP 连接建立 |
| 服务端 `accept` 返回 | 握手已经完成，连接可由应用领取 | API 与监听队列 |
| 客户端 `sendall(16 bytes)` 返回 | 可找到合计16字节的客户端方向数据 | API 与线上报文 |
| 服务端 `recv_frame` 返回 | 请求帧已完整交给服务端应用 | 应用读取 |
| 服务端 `sendall(16 bytes)` 返回 | 可找到合计16字节的服务端方向数据 | API 与线上报文 |
| Socket 上下文结束 | 本程序正常结束时可见连接释放相关报文 | API 与 TCP 状态迁移 |

时间戳允许存在细小差异。数据报文可能在 `sendall` 返回日志写出前已经经过捕获点，连接释放报文也可能紧邻 `close` 调用发生。日志中的 `sendall` 返回表达本地提交完成；Wireshark 观察报文经过捕获点；对端日志中的 `recv` 返回表达字节已交付给对端应用。三者按层次排列后，一条请求路径就变得可解释。

## 常见观察偏差

### 抓包列表为空

先确认接口。目标是 `127.0.0.1` 时应使用回环捕获接口。再清空显示过滤器，检查原始抓包是否有数据，并核对程序实际端口。

### 重新捕获完整握手

捕获可能在客户端启动后才开始。重新启动捕获，再运行一组新的服务端与客户端。完整连接分析应覆盖首个 SYN 到最后的关闭报文。

### 同一端口出现多条流

每次运行都会获得新的客户端临时端口。先根据日志锁定四元组，再选中对应报文，使用 `tcp.stream == N` 聚焦唯一连接。

### 实际数据报文数量发生变化

ACK 合并、数据分段、FIN 合并以及操作系统调度都允许改变报文数量。分析时按字节范围与状态含义推进，具体行数作为本次观察结果记录。

### Wireshark 显示校验和提示

本机抓包可能在网卡或协议栈完成校验和处理之前取得报文副本，卸载功能会影响显示。第13章会结合伪首部与 Checksum Offload 详细判断。

## 保存实验材料

建议用清晰名称保存四项材料：

```text
tcp-ch06-server.log
tcp-ch06-client.log
tcp-ch06-connections.txt
tcp-ch06-loopback.pcapng
```

Wireshark 选择 **File → Save As** 保存 `pcapng`。日志可以在运行时通过 PowerShell `Tee-Object` 同时显示并写入：

```powershell
python -X utf8 .\server.py 2>&1 | Tee-Object -FilePath .\tcp-ch06-server.log -Encoding UTF8
```

客户端采用相同方式更换文件名。连接持续时间很短时，可以使用第5章“先完成握手，后调用 accept”的暂停版本查询状态；保存证据后再按 Enter 继续。

## 理解检查

1. 程序连接 `127.0.0.1` 时应优先选择哪类抓包接口？
2. `tcp port 50007` 与 `tcp.port == 50007` 分别属于哪类过滤器？
3. 同一抓包里多次运行程序，怎样锁定其中一条连接？
4. `tcp.len == 0` 的报文是否仍可能推进连接状态？
5. `tcp.analysis.retransmission` 属于线上首部字段还是分析器推断？
6. Follow TCP Stream 中的颜色与应用消息边界分别由什么决定？

### 参考答案

1. Npcap 提供的 Windows 回环捕获接口。
2. 前者是捕获过滤器，后者是显示过滤器。
3. 先用日志中的四元组找到报文，再使用该报文的 `tcp.stream` 编号过滤。
4. 可以。SYN、纯 ACK、FIN 等报文的 TCP 数据长度可以为零，标志位与序列空间仍有作用。
5. 它是 Wireshark 根据抓包上下文生成的分析标记。
6. 颜色区分两个传输方向；应用协议的4字节长度字段决定本程序的消息边界。

## 本章小结

第一次抓包的核心方法可以浓缩成四步：选对抓包点，用端口找到候选流，用四元组和 `tcp.stream` 锁定唯一连接，再把报文时间线与两端日志对齐。完成这一步后，Socket API、操作系统状态与线上 TCP 报文已经出现在同一幅图中。第三篇将复用这份抓包，逐字段拆解每一个 TCP 首部。
