# 第33章 常见故障案例

故障名称只是入口。同一个“连接超时”可能来自路径丢弃、防火墙策略、目标地址错误或主机过载；同一条重传标记也可能来自真实丢包和本机捕获缺口。有效诊断会把现象放回连接阶段，并设计能够区分候选原因的验证实验。

## 一、统一排障模板

每个案例都按以下九项记录：

1. **现象**：错误文本、发生时间、频率、影响用户与业务指标。
2. **阶段**：名称解析、路由、握手、数据传输、应用处理或连接释放。
3. **候选原因**：只列能解释当前证据的原因，并标注优先级。
4. **抓包特征**：引用抓包点、四元组、帧号、Seq/Ack、窗口和时间。
5. **系统状态**：监听地址、连接状态、队列、资源和防火墙计数。
6. **应用检查点**：读取完成、处理完成、写入、超时与关闭日志。
7. **验证实验**：每次改变一个变量，优先选择成本低且区分度高的实验。
8. **处理方法**：对应已经确认的机制。
9. **副作用与回归**：记录安全范围、资源成本、延迟和故障恢复表现。

下面的快速定位表可以决定第一步看哪里：

| 抓包时间线 | 当前阶段 | 首要检查 |
| --- | --- | --- |
| 正确接口上没有 SYN | TCP 调用之前或路由之前 | DNS、目标地址、应用日志、路由、抓包范围 |
| SYN 后立即收到 RST+ACK | 建立连接 | 监听状态、目标端口、防火墙 reject |
| 多次 SYN，始终没有响应 | 建立连接 | 双向路径、防火墙 drop、主机可用性、队列压力 |
| 握手成功后立即 RST | 会话开始 | 服务端日志、协议校验、进程重启、代理策略 |
| 请求数据很快得到 TCP ACK，业务响应迟到 | 应用处理 | 服务端读取、队列、数据库、锁和下游调用 |
| 接收方通告窗口降为 0 | 数据传输 | 接收应用读取速度、接收缓冲与资源压力 |
| 对端 FIN 后本地长期 CLOSE_WAIT | 连接释放 | 本地应用关闭路径、线程和资源回收 |

## 二、连接建立类故障

### 1. Connection refused

典型时间线是客户端发出 SYN，目标很快返回 `RST, ACK`。这通常说明报文到达了某个能明确拒绝连接的节点：目标端口没有监听，防火墙使用 reject，或转发设备主动拒绝。若本机连接本机未监听端口，操作系统也会快速返回拒绝错误。

```text
tcp.flags.syn == 1 || tcp.flags.reset == 1
```

服务端执行：

```powershell
$listener = Get-NetTCPConnection -State Listen |
  Where-Object LocalPort -eq 9000 |
  Select-Object -First 1
if ($listener) {
  $listener | Format-Table LocalAddress, LocalPort, OwningProcess
  Get-Process -Id $listener.OwningProcess
} else {
  Write-Output '未找到监听 9000 端口的 TCP Socket'
}
```

`127.0.0.1:9000` 只接受 IPv4 回环路径；远程客户端需要服务监听可达接口地址，或按设计监听 IPv4 通配地址。调整绑定范围会扩大可访问面，应同步检查主机防火墙、身份认证和暴露边界。

相似现象是握手成功后收到 RST。区分证据很直接：refused 的 RST 出现在 SYN 之后，应用拒绝或异常关闭的 RST 出现在三次握手之后。后者应继续查服务端 accept、协议校验和进程生命周期日志。

### 2. 连接超时与 SYN 重传

客户端按重传计时器多次发送相同 SYN，抓包中始终缺少 SYN+ACK 或 RST，最终连接调用超时。候选原因包括路由黑洞、防火墙 drop、目标主机离线、回程路径故障，以及服务器 SYN 处理能力或队列压力。

```powershell
Test-NetConnection 10.0.0.8 -Port 9000 -InformationLevel Detailed
Get-NetRoute -AddressFamily IPv4 | Sort-Object RouteMetric
```

最小验证顺序为：确认客户端正确接口上确实发出 SYN；在服务端入口抓包确认 SYN 是否到达；若到达，再查监听、SYN_RECV 状态、队列与主机资源；若服务端已发 SYN+ACK，则沿回程路径寻找消失位置。`ping` 成功只覆盖当前大小和方向的 ICMP 测试，TCP 端口仍需独立验证。

相似现象是 DNS 解析等待。此时 TCP 抓包中通常还没有目标 SYN，DNS 报文、解析日志和连接调用时间分段可以给出区分证据。

### 3. 握手后立即 RST

常见原因有服务进程在 accept 后执行 abortive close、应用协议首包校验失败、代理访问策略拒绝、进程崩溃或重启。记录 RST 前最后一段数据、RST 的方向、Seq/Ack 是否位于当前窗口，以及两端日志。仅凭 RST 的 IP 地址很难确认具体进程来源，有状态防火墙或代理也可能生成复位。

验证实验可使用一个符合协议的最小客户端与一个故意发送错误首包的客户端进行对照。修复后还要回归正常请求、错误请求、服务重启和连接池恢复行为。

## 三、连接释放类故障

### 1. 大量 CLOSE_WAIT

本地进入 CLOSE_WAIT 说明本地 TCP 已收到对端 FIN，并把“对端不会继续发送”这一事件交给应用；本地应用仍持有 Socket，尚未完成自己的关闭。少量短暂 CLOSE_WAIT 属于关闭过程的一部分，数量持续增长通常指向异常路径遗漏 `close()`、线程长期阻塞或资源清理停滞。

```powershell
Get-NetTCPConnection -State CloseWait |
  Group-Object OwningProcess | Sort-Object Count -Descending
```

抓包中找对端 FIN 及本地 ACK，再把四元组映射到进程、线程栈和请求日志。处理重点是让所有成功、超时、解析错误和取消路径都进入确定的资源回收流程。直接终止进程可以清理存量连接，同时会中断该进程正在处理的其他请求。

### 2. 大量 TIME_WAIT

TIME_WAIT 常出现在执行主动关闭的一端，用于吸收旧连接的延迟报文，并允许最终 ACK 丢失后再次响应 FIN。高请求率配合短连接会自然产生较多 TIME_WAIT。诊断时统计创建速率、目标四元组分布、临时端口范围和连接失败率。

连接复用可以减少握手、TLS 和关闭开销。缩短系统级 TIME_WAIT 或扩大端口复用范围会改变整台主机的连接安全边界，应在压测、故障注入和回滚方案齐备后评估。相似现象是 CLOSE_WAIT；两者的区分字段是状态名、FIN 方向和本地应用是否已调用关闭。

### 3. 空闲连接成为陈旧连接

主机崩溃、移动网络切换或中间设备清除状态后，一端仍可能暂时保留 ESTABLISHED。下一次发送可能经历重传后超时，也可能立即收到 RST。对比防火墙、NAT、负载均衡的空闲超时与连接空闲时长，并用受控空闲实验复现。第37章会进一步设计 TCP Keepalive、应用心跳和业务健康检查。

## 四、数据传输类故障

### 1. 读取长期阻塞与双方互相等待

常见现场是双方连接保持 ESTABLISHED，窗口正常，抓包也没有丢包；客户端等待响应，服务端仍在等待请求剩余部分。长度字段写错、分隔符缺失、只调用一次 `recv()`、半关闭约定不一致都能造成这一状态。

使用 `Follow TCP Stream` 还原字节，并按协议规则手工计算：长度前缀声明多少、实际到达多少、接收循环还期待多少。应用日志应记录“首字节到达”“完整帧到达”和“开始业务处理”三个时间点。给读取操作设置总截止时间，并在错误日志中保存已收字节数，可以把永久等待转成可定位事件。

### 2. Zero Window

接收方通告 `Win=0` 表示其 TCP 接收缓冲暂时没有可用空间。发送方会停止普通数据推进，并周期性发送 Zero Window Probe；接收方恢复读取后通告非零窗口。

```text
tcp.window_size == 0 || tcp.analysis.zero_window_probe || tcp.analysis.window_update
```

检查接收应用是否被慢数据库、锁、磁盘或下游队列阻塞，也要查看内存压力和 Socket 缓冲配置。提高缓冲区可以吸收更长突发，同时增加每连接内存和排队时延。相似现象是拥塞窗口受限：此时接收窗口仍有余量，丢包、RTT 与在途字节更能解释发送停顿。

### 3. 持续重传、乱序和吞吐量低

先按第32章核对抓包完整性与卸载。真实丢包常伴随相同 Seq 范围再次发送、重复 ACK 或 SACK、在途数据回退和吞吐下降；网络乱序则表现为缺口段稍后到达，累计 ACK 随后推进。两端抓包可以确认报文是在发送前、路径中还是接收后变得不可见。

低吞吐还可能来自应用写入间隔、磁盘供给、CPU、接收窗口、拥塞窗口、RTT 与带宽时延积。记录每秒应用产出、发送速率、`Bytes in flight`、窗口、RTT 和重传率，再判断限制环节。

小请求交互偶发停顿时，关注小写入、Nagle 算法与 Delayed ACK 的时间组合。受控 A/B 实验可比较聚合写入与 `TCP_NODELAY`；启用后通常增加包率和首部开销，回归测试应同时观察延迟分位数与每秒包数。

## 五、应用协议与重试故障

长度前缀声明 1000 字节、发送方只交付 800 字节时，TCP 可以可靠确认已经收到的 800 字节，接收应用会继续等待剩余 200 字节。协议实现需要限制最大长度、循环读取、识别 EOF，并把“声明长度、已收长度、连接 ID”写入错误日志。

另一个典型现场是服务端已经完成扣款，响应在返回途中丢失，客户端超时后使用新连接重试，于是出现两次业务操作。两次 TCP 连接各自都可能完全正常。请求 ID、幂等键、服务端去重记录和事务日志负责建立业务上的唯一性。超时只说明客户端在期限内没有取得结果，业务最终状态应通过幂等重试或状态查询确认。

## 实验：四份最小故障报告

分别复现以下场景，并为每份报告填写统一模板：

1. 连接一个本机未监听端口，记录 SYN、RST 与系统监听表。
2. 服务端建立连接后暂停读取，客户端持续发送足够多的数据，记录接收窗口从收缩到恢复的变化。
3. 发送一个长度大于实际载荷的帧，记录双方等待点和总截止时间。
4. 服务端完成操作后主动丢弃响应，客户端带同一请求 ID 重试，验证去重结果。

每个案例再列出一个相似现象，并写出能够区分两者的具体帧、状态或日志事件。

## 理解检查

1. SYN 后的 RST+ACK 与握手后的 RST 分别指向哪些检查点？
2. 服务端入口已经看到 SYN+ACK 发出，客户端仍持续重传 SYN，下一步应检查哪段路径？
3. CLOSE_WAIT 长期增长时，哪一端的应用关闭路径最值得检查？
4. Zero Window 和网络拥塞造成的停顿可以用哪些字段区分？
5. TCP 流完全正常时，为什么超时重试仍可能产生重复业务操作？
