# 第34章 TCP 性能调优的边界

性能调优从一个可测量的业务目标开始，例如“并发 200 时，请求端到端 p99 小于 300 ms”或“40 ms RTT 的专线上，单连接文件传输有效吞吐达到 80 Mbit/s”。目标明确后，抓包、系统指标和应用日志才能共同回答：时间消耗在哪里，哪一种资源限制了进度，一项改动是否真的改善了用户结果。

TCP 参数位于整条处理链中的一段。应用排队、数据库、CPU、内存、磁盘、锁竞争、序列化、日志、网络带宽、RTT、丢包、中间设备和连接创建频率都可能决定最终表现。

## 一、先定义指标和负载

一份基线至少写清以下条件：

- 请求或文件大小、数据分布、连接数、并发数和持续时间；
- 客户端、服务端、网络路径、代理与 TLS 配置；
- 冷启动、预热、稳定测量和收尾阶段的边界；
- 成功率、错误类型、超时阈值和重试策略；
- 目标指标及分位数，例如 p50、p95、p99；
- 软件版本、内核版本、网卡驱动和关键参数快照。

平均值会压缩长尾信息。延迟优化应保留直方图或足够细的分位数，并把失败请求也纳入结果。吞吐需要区分：

- **应用有效吞吐**：单位时间内完成交付的业务载荷；
- **TCP 发送速率**：单位时间内发送的 TCP 字节；
- **链路线速**：包括 TCP/IP 首部、链路首部、重传和其他流量。

一次测试可以得到很高的瞬时值，稳定结论还需要多轮重复、固定负载和误差范围。

## 二、按端到端路径拆分时间

请求总时间可以组织为：

$$
T_{total}=T_{queue}+T_{connect}+T_{tls}+T_{request}+T_{service}+T_{response}
$$

其中每一项都可以继续拆分。`T_service` 可能包含应用队列、数据库、锁和下游调用；`T_request` 与 `T_response` 可能受到 RTT、窗口、拥塞、丢包和应用写入节奏影响。

建议按以下顺序定位：

1. 核验压测工具自身的 CPU、连接上限、数据生成速度和计时方式。
2. 用请求 ID 对齐客户端与服务端日志，拆出排队、处理和下游耗时。
3. 同步采集 CPU、内存、GC、磁盘、锁、线程池、数据库池和应用队列。
4. 测量路径可用带宽、RTT、丢包、乱序与 MTU。
5. 检查接收窗口、在途字节、重传、连接建立频率和关闭状态。
6. 结合中间设备日志确认限速、连接池、空闲回收和代理排队。

若服务端在收到完整请求后 800 ms 才开始写响应，而网络往返只需 10 ms，应用处理链具有更高的优化优先级。若应用持续准备好数据、CPU与磁盘有余量，同时发送进度规律地受窗口或丢包限制，TCP 与路径分析的优先级会上升。

## 三、需要共同观察的指标

| 指标 | 含义 | 常见证据 |
| --- | --- | --- |
| p50 / p95 / p99 延迟 | 典型体验与长尾 | 客户端直方图、请求 ID 时间线 |
| 有效吞吐 | 真正完成的业务字节 | 应用计数器、文件哈希与耗时 |
| RTT | 确认反馈所需时间 | 两端测量、`tcp.analysis.ack_rtt`、主机 TCP 信息 |
| 重传率 | 额外发送及恢复代价 | 两端抓包、系统 TCP 计数器 |
| 接收窗口 rwnd | 接收端允许的未确认数据范围 | `tcp.window_size`、Zero Window、Window Update |
| 拥塞窗口 cwnd | 发送端按网络反馈控制的在途上限 | Linux `ss -ti`、内核遥测；抓包只能辅助推断 |
| Bytes in flight | 已发送且尚未累计确认的数据 | Wireshark 计算字段、Seq/Ack 时间线 |
| Socket 与应用队列 | 数据或任务在哪一侧排队 | Send-Q/Recv-Q、线程池、连接池、业务队列 |
| 主机资源 | 本机处理能力与争用 | CPU、内存、磁盘、上下文切换、GC、软中断 |

Wireshark 可导出关键序列：

```powershell
tshark -r .\perf.pcapng -Y "tcp.stream eq 12" -T fields `
  -e frame.number -e frame.time_relative -e tcp.seq -e tcp.ack -e tcp.len `
  -e tcp.window_size -e tcp.analysis.bytes_in_flight -e tcp.analysis.ack_rtt `
  -e tcp.analysis.retransmission
```

Windows 可以保存连接与主机基线：

```powershell
netsh interface tcp show global
Get-NetTCPConnection | Group-Object State | Sort-Object Count -Descending
Get-Counter '\Processor(_Total)\% Processor Time', `
            '\Memory\Available MBytes', `
            '\TCPv4\Segments Retransmitted/sec' -SampleInterval 1 -MaxSamples 60
```

Windows 性能计数器路径会随系统显示语言变化，可以先运行 `Get-Counter -ListSet *` 查找当前系统中的处理器、内存和 TCP 计数器名称。

Linux 上的 `ss -ti` 常能展示某条连接的 RTT、cwnd、重传和 pacing 信息。跨平台报告应同时记录命令、权限、采样周期和字段单位。

## 四、带宽时延积给出的窗口尺度

带宽时延积 BDP 表示维持链路持续繁忙所需的大致在途数据量：

$$
\mathrm{BDP\ (bytes)}=\frac{\mathrm{Bandwidth\ (bit/s)}\times\mathrm{RTT\ (s)}}{8}
$$

例如带宽为 `100 Mbit/s`、RTT 为 `40 ms`：

$$
\mathrm{BDP}=\frac{100\,000\,000\times0.04}{8}=500\,000\ \mathrm{bytes}\approx488\ \mathrm{KiB}
$$

若单连接长期只能维持约 64 KiB 在途数据，其理想上限约为：

$$
\frac{64\ \mathrm{KiB}}{0.04\ \mathrm{s}}\approx1.56\ \mathrm{MiB/s}
$$

这个计算给出数量级线索。实际在途上限还受到拥塞窗口、接收窗口、发送与接收缓冲、应用供给速度、丢包和调度影响。抓包中应读取经过 Window Scale 换算后的窗口；缺少握手时，缩放因子需要标记为未知。

## 五、常见调优项及适用边界

### 1. 发送与接收缓冲区

高带宽、高 RTT 路径需要容纳足够的在途数据。证据组合包括：应用持续有数据、接收窗口或发送缓冲形成稳定上限、重传较少、吞吐接近“可用窗口 ÷ RTT”的估算值。

现代系统通常提供自动调节机制，应用自行固定很小的缓冲值可能限制其发挥。增大缓冲会提高每连接内存占用，也可能让排队数据积累更久。调优后同时观察吞吐、内存、尾延迟和拥塞时的恢复。

### 2. TCP_NODELAY 与应用写入聚合

Nagle 算法倾向于在仍有未确认小数据时聚合后续小写入，能够降低小包数量。请求—响应式协议若频繁产生很小写入，并与 Delayed ACK 形成等待组合，`TCP_NODELAY` 可能降低交互延迟。

验证时记录每次应用写入时间、线上小段数量、ACK 节奏和延迟分位数。启用 `TCP_NODELAY` 可能提高每秒包数、首部开销和 CPU 中断压力。应用仍可把同一逻辑消息的多个小字段聚合成一次写入。

### 3. 连接复用

复用连接可以减少 TCP 握手、TLS 握手、慢启动和端口 churn，适合连续请求。它也会带来连接池容量、空闲连接有效性、请求排队和单连接故障影响范围等设计问题。测试应包含稳定流量、突发流量、代理空闲回收、服务重启和连接池恢复。

### 4. 并发度

增加并发连接或并行请求可以隐藏等待、提高磁盘与网络利用率。并发超过下游容量后，队列、锁竞争、数据库连接等待、丢包和长尾通常会上升。逐级提升并发并绘制“吞吐—延迟—错误率”曲线，曲线拐点比单个峰值更适合确定生产上限。

### 5. 系统级 TCP 参数

拥塞控制算法、自动调窗、临时端口、重传和 Keepalive 等系统设置具有主机级影响。采用这类调整前，应保存原值、适用接口和工作负载，确认应用与路径证据指向相应机制，并准备单机灰度与即时回滚。云平台、容器和代理还可能拥有独立限制，需要一并纳入测试矩阵。

## 六、一次可复查的 A/B 调优

假设跨地域文件传输的目标为 `≥ 8 MiB/s`，基线只有 `1.5 MiB/s`。已知 RTT 约 40 ms，路径容量 100 Mbit/s，应用供给稳定，CPU 和磁盘低于 50%，抓包无持续重传，缩放后的接收窗口长期约 64 KiB。

1. 用 `64 KiB ÷ 40 ms` 算得约 `1.56 MiB/s`，与基线同量级。
2. 在接收主机核验自动调窗与应用 `SO_RCVBUF` 配置，确认应用固定值限制了窗口增长。
3. 只移除该固定值，保持文件、并发、路径和软件版本一致。
4. 完成预热后重复测试五轮，记录有效吞吐、p99、窗口、重传和内存。
5. 若窗口增长到 BDP 附近且吞吐稳定提升，证据支持该改动；若窗口已增长而吞吐仍低，继续检查 cwnd、应用供给和路径限速。
6. 在 1%、10%、100% 负载逐级验证，并保留恢复原配置的操作。

这个过程把估算、主机事实、单项变更和结果闭合在同一条证据链中。

## 七、调优报告与停止条件

```text
业务目标：并发200，成功率≥99.9%，p99≤300 ms
基线条件：版本、主机、数据集、路径、持续时间、预热方式
基线结果：吞吐、p50/p95/p99、错误率、重传、RTT、窗口、资源
瓶颈假设：机制、支持证据、反例、证据边界
单项改动：配置位置、旧值、新值、影响范围、回滚步骤
A/B结果：重复次数、分位数、误差范围、资源与异常指标
结论：目标改善幅度、适用负载、灰度计划、继续观察项
```

出现以下情况时可以结束当前轮次：业务目标已经稳定满足；新增改动的收益落入测量噪声；瓶颈证据已经转向应用、数据库或路径容量；副作用超过收益；现有观测无法区分候选原因，需要先补遥测或增加抓包点。

## 实验：比较聚合写入与 TCP_NODELAY

1. 编写客户端，每个请求连续写入 8 个小字段；服务端收到完整帧后立即响应。
2. 固定请求数、并发、消息内容和服务端处理逻辑，完成预热。
3. 分别测试默认设置、应用聚合为一次写入、启用 `TCP_NODELAY` 三组配置。
4. 每组重复五轮，记录 p50/p95/p99、每秒请求数、每秒包数、平均段长和 CPU。
5. 检查抓包中的写入时间、小段、Delayed ACK 与响应时间线。
6. 给出适用于当前负载的选择，并写明包率、CPU和长尾变化。

## 理解检查

1. 为什么 TCP 调优需要从业务 SLO 与可重复负载开始？
2. 有效吞吐、TCP 发送速率和链路线速各自包含哪些字节？
3. BDP 为 500 KiB 时，单连接长期只有 64 KiB 在途数据意味着什么？
4. 抓包可以怎样帮助判断 rwnd，为什么 cwnd 还需要主机遥测？
5. 启用 `TCP_NODELAY` 后应同时观察哪些收益与成本？
6. 一项系统级参数改动进入生产前，应准备哪些灰度和回滚证据？
