# 第24章 延迟、吞吐量和带宽时延积

一条链路标称 1 Gbit/s，跨地域复制文件却只达到几十 Mbit/s。带宽描述瓶颈每秒可传送多少比特，TCP 还需要在每个 RTT 内保持足够多的数据在途。窗口、往返时延、丢包恢复、传输规模和应用供数共同决定最终吞吐。

## 先统一三个量

### 延迟

TCP 分析最常用 RTT，即发送数据到收到相应确认的往返时间。应用请求延迟还包含排队、协议轮次、服务端处理和客户端调度。单向延迟需要两端时钟同步，单侧抓包通常更适合可靠计算 RTT。

路径延迟可以拆成几类直觉量：

- **传播延迟**：信号沿介质传播所需时间；
- **序列化延迟**：把一个报文的全部比特推上链路所需时间；
- **排队延迟**：报文等待瓶颈处理的时间；
- **主机处理延迟**：协议栈、应用和调度所用时间。

在 10 Mbit/s 链路上发送 1500 字节，单次序列化时间为：

$$
\frac{1500\times8\text{ bit}}{10\,000\,000\text{ bit/s}}
=0.0012\text{ s}=1.2\text{ ms}
$$

带宽提高会降低序列化时间，地理传播距离与排队仍会贡献延迟。

### 吞吐量与有效吞吐

吞吐量需要明确测量层次。链路吞吐可包含 Ethernet、IP、TCP 首部与重传；应用有效吞吐通常用成功交付的应用字节除以总时间：

$$
\text{goodput}=\frac{\text{成功交付的应用字节}}{\text{传输持续时间}}
$$

`iperf3`、应用日志和 Wireshark I/O Graph 可能采用不同分子与时间边界。报告中同时写明单位、数据层次、开始结束事件，数字才具备可比性。

### 瓶颈带宽

端到端路径由多条链路、队列和设备组成，最窄的长期服务速率形成瓶颈。发送端网卡显示 1 Gbit/s，只说明本地接口速率；VPN、Wi-Fi、出口整形、跨区线路或接收端入口都可能形成更低上限。

## BDP 表示路径上能容纳的在途量

带宽时延积的核心公式为：

$$
BDP=\text{瓶颈带宽}\times RTT
$$

单位需要先统一。以 100 Mbit/s、RTT 80 ms 为例：

$$
100\times10^6\text{ bit/s}\times0.080\text{ s}
=8\times10^6\text{ bit}
$$

$$
\frac{8\times10^6}{8}=1\,000\,000\text{ byte}
\approx0.954\text{ MiB}
$$

这表示发送端约需维持 1 MB 未确认数据，ACK 时钟才能持续填满 100 Mbit/s 路径。再看 1 Gbit/s、100 ms：

$$
1\times10^9\times0.1=100\times10^6\text{ bit}
=12.5\text{ MB}\approx11.92\text{ MiB}
$$

高带宽、高 RTT 路径需要更大的窗口和缓冲能力，因此常称为长肥网络。Window Scale 为大接收窗口提供线上表达能力，拥塞控制仍需逐步建立足够的 `cwnd`。

## 单位换算的固定流程

性能计算最常见的偏差来自 bit、byte、十进制前缀和二进制前缀混用。可以固定采用四步：先把带宽化成 bit/s；把 RTT 化成秒；相乘得到 bit；除以 8 得到 byte。展示结果时同时保留十进制 MB 与二进制 MiB。

常用关系如下：

| 名称 | 数值 |
| --- | ---: |
| 1 byte | 8 bit |
| 1 Mbit/s | $10^6$ bit/s |
| 1 MB | $10^6$ byte |
| 1 MiB | $2^{20}=1\,048\,576$ byte |
| 1 ms | $10^{-3}$ s |

例如 25 Mbit/s 与 40 ms 相乘：$25\times10^6\times0.04=1\times10^6$ bit，再除以 8 得 125000 byte，约 122 KiB。若直接把 25 当成 MB/s，结果会扩大 8 倍。每行算式带上单位，可以在约分过程中及时发现这类偏差。

BDP 描述一个数据方向维持 ACK 流水线所需的在途量。全双工连接的两个方向各有自己的数据速率、接收窗口和拥塞状态，应分别计算；反向 ACK 所走路径的延迟也计入正向数据的 RTT。

报告带宽时建议同时写成 `Mbit/s` 与 `MiB/s`。例如 80 Mbit/s 除以 8 得 10 MB/s，再除以 1.048576 约为 9.54 MiB/s。这样可以直接与应用按字节记录的文件大小和耗时核对。

保留原始单位和换算过程，也方便团队成员复核每一步。

## 窗口怎样形成吞吐上限

当窗口是主要限制，稳定状态下可用一个近似式估算吞吐上限：

$$
\text{throughput}\lesssim\frac{\min(rwnd,cwnd)}{RTT}
$$

假设有效窗口只有 256 KiB，RTT 为 80 ms：

$$
\frac{256\times1024\text{ byte}}{0.08\text{ s}}
=3\,276\,800\text{ byte/s}
$$

$$
3\,276\,800\times8
=26\,214\,400\text{ bit/s}\approx26.2\text{ Mbit/s}
$$

即使链路可提供 100 Mbit/s，这个窗口也只能支撑约 26.2 Mbit/s 的理想上限。要接近链路容量，`rwnd`、`cwnd` 和实际在途数据都需要达到约 1 MB，同时应用持续供数、恢复开销较低。

观察到的 RTT 若包含深队列产生的额外延迟，按它计算的 BDP 会连队列容量一起算入。性能建模常同时记录最小 RTT 和当前 RTT：最小值更接近传播路径，差值可提示排队增长。

## 不同业务形态的限制

| 场景 | 主要关注点 | 有效改进方向 |
| --- | --- | --- |
| 大文件长连接 | BDP、窗口、丢包、磁盘与应用供数 | 足够缓冲、持续流水线、定位重传 |
| 小文件短连接 | 握手、慢启动、连接复用 | 复用连接、减少协议轮次 |
| 小请求串行执行 | 每次请求至少经历的 RTT 与处理时间 | 流水线、合理并发、批处理 |
| 高 RTT 卫星或跨洲路径 | 大 BDP、恢复时间、窗口扩展 | 大窗口、适配的拥塞控制、稳定供数 |
| 接收应用较慢 | `rwnd`、Zero Window、业务队列 | 端到端背压、有限队列、提升消费能力 |

假设纯网络 RTT 为 20 ms，100 个请求严格串行，每个请求都等前一个响应后再发。仅按一个 RTT 的理想下界计算，网络轮次已占约：

$$
100\times20\text{ ms}=2\text{ s}
$$

若协议允许 10 个请求并行，理想情况下可分成约 10 轮，网络轮次约 0.2 秒，再叠加服务处理与调度。并发连接或多路请求能更早形成足够在途工作，同时会增加服务端负载、队列和公平性压力，容量设计需要一起完成。

慢启动对短传输尤其重要。连接可能在 `cwnd` 仍较小时就完成，长期链路带宽尚未被充分利用。大文件有更多 RTT 让窗口增长并进入稳态。应用读写块大小主要影响系统调用次数、复制开销和供数连续性，TCP 分段边界仍由协议栈与路径条件决定。

## 受控实验：改变 RTT、并发度和读写块

复用 `tcp-rx` 实验拓扑。第23章的服务端仍在运行时直接复用；当前端口空闲时在终端 A 启动服务端：

```bash
sudo ip netns exec tcp-rx iperf3 -s -B 10.200.20.2
```

终端 B 抓取全部实验，终端 C 运行测试：

```bash
sudo tcpdump -i veth-tx -s 0 -w chapter24.pcap 'tcp port 5201'
```

下面把正向瓶颈固定为 50 Mbit/s，分别配置 10、50、100 ms 单向延迟，对应约 20、100、200 ms 基础 RTT。每组传输固定为 64 MiB：

```bash
for one_way in 10ms 50ms 100ms; do
  sudo tc qdisc replace dev veth-tx root netem delay "$one_way" rate 50mbit limit 10000
  sudo ip netns exec tcp-rx tc qdisc replace dev veth-rx root netem delay "$one_way" limit 10000

  iperf3 -c 10.200.20.2 -n 64M -P 1 -l 128K -i 0.5
  iperf3 -c 10.200.20.2 -n 64M -P 4 -l 128K -i 0.5
  iperf3 -c 10.200.20.2 -n 64M -P 1 -l 4K -i 0.5
done
```

`-P 4` 创建 4 条并行 TCP 连接；`-l` 控制 `iperf3` 每次读写缓冲区的长度，它不承诺对应线上报文段大小。三种 RTT 对应的理论 BDP 为：

| 50 Mbit/s 路径 | 计算 | BDP |
| --- | --- | ---: |
| RTT 20 ms | $50\times10^6\times0.02/8$ | 125000 B，约 122 KiB |
| RTT 100 ms | $50\times10^6\times0.10/8$ | 625000 B，约 610 KiB |
| RTT 200 ms | $50\times10^6\times0.20/8$ | 1250000 B，约 1.19 MiB |

### 记录表

每次测试记录以下字段：

| RTT | 并行数 | `-l` | 总耗时 | 应用吞吐 | 重传 | 峰值 `cwnd`（段/字节） | `rwnd` 最小值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 20 ms | 1 | 128 KiB |  |  |  |  |  |
| 100 ms | 1 | 128 KiB |  |  |  |  |  |
| 200 ms | 1 | 128 KiB |  |  |  |  |  |
| 各 RTT | 4 | 128 KiB |  |  |  |  |  |
| 各 RTT | 1 | 4 KiB |  |  |  |  |  |

传输时用 `ss -ti dst 10.200.20.2` 采样 RTT、`cwnd`、MSS、pacing 和重传字段。Linux `ss` 通常按报文段显示 `cwnd`，记录表同时保存原值以及乘以 MSS 后的近似字节数。在 Wireshark 中使用 `Statistics → TCP Stream Graphs → Throughput` 查看随时间的增长，再从 Seq/Ack 计算选定时刻的在途字节。

### 预期解释

- RTT 增大后，每轮窗口反馈需要更长时间；固定大小传输更容易受到慢启动和窗口限制。
- 四条并行连接各自维护 `cwnd`，聚合在途量可能更快接近 BDP；总速率仍受 50 Mbit/s 瓶颈约束。
- 较小应用块会增加调用频率，也可能让应用供数变得零散；实际差异随语言、CPU和内核缓冲策略变化。
- `rwnd`、`cwnd` 均达到 BDP 量级且应用持续供数时，长传输更有机会接近瓶颈速率。

全部测试结束后，在服务端与抓包终端按 `Ctrl+C`，再清理实验环境：

```bash
sudo tc qdisc del dev veth-tx root
sudo ip netns exec tcp-rx tc qdisc del dev veth-rx root
sudo ip netns del tcp-rx
```

若环境缺少 `netem`，选择两台自己控制、RTT 不同的主机运行同样的固定数据量测试，或在一台远端主机上比较串行请求与有限并发。使用三次握手/ACK 时间或 `ss -ti` 测 RTT，以实测吞吐估计瓶颈，再完成 BDP 和窗口上限计算。Windows 可用 Wireshark I/O Graph、应用日志和 PowerShell 时间测量形成对应证据。

## 一套低吞吐诊断顺序

1. 用应用成功交付字节和总时间计算有效吞吐，写明单位。
2. 记录最小 RTT、当前 RTT 和瓶颈带宽估计，计算 BDP。
3. 比较缩放后的 `rwnd`、发送端 `cwnd`、FlightSize 与 BDP。
4. 检查重传、SACK、RTO 和拥塞事件对窗口的影响。
5. 检查应用是否持续供数、接收是否及时、CPU与存储是否达到上限。
6. 改变一个变量再复测，保留基线和完整时间序列。

## 理解检查

1. 200 Mbit/s、RTT 40 ms 的 BDP 是多少比特、多少十进制 MB？
2. 512 KiB 窗口、RTT 100 ms 时，窗口限制下的理想吞吐约为多少 Mbit/s？
3. 当前 RTT 80 ms、最小 RTT 30 ms，这 50 ms 差值可以提出哪项路径假设？
4. 为什么 10 KB 短请求和 10 GB 文件即使走同一路径，也会呈现不同带宽利用率？
5. `iperf3 -l 4K` 在应用层控制什么，线上 TCP 分段还由哪些因素决定？

## 小结

BDP 把瓶颈带宽和 RTT 合成“填满路径所需在途数据”。有效窗口低于 BDP 时，吞吐近似受窗口除以 RTT 限制；窗口充足后，拥塞控制、丢包、应用供数和处理资源继续决定结果。性能结论需要统一单位、明确测量层次，并用应用、端点状态和抓包三类证据共同支持。
