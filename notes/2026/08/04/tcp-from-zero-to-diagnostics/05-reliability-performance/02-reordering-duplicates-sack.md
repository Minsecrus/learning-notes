# 第21章 乱序、重复数据和 SACK

接收端先看到了 Seq 3001，过了一会儿才看到 Seq 2001。发送端可能遇到丢包，也可能只是前一个报文段走得更慢。TCP 需要先保存当前事实，再等待足够证据决定恢复。本章从接收队列出发，读懂累计 Ack 与 SACK 共同描述的“连续前缀、缺口和已到达区间”。

## 乱序从哪里来

同一连接中的报文段可以因多种原因改变到达顺序：

- 链路层重传让前一个帧多等了一轮；
- 路由变化、链路聚合或多路径调度让相邻报文经历不同延迟；
- 主机的并行收包、卸载、队列调度让抓包点呈现不同处理顺序；
- 某个数据段已丢失，后续段继续到达，于接收端形成与乱序相同的初始形状。

抓包缺帧还会制造“看起来缺了一段”的观察结果。因此，乱序首先是一种到达现象；是否发生真实丢包，需要继续观察缺口是否自行补齐、发送方是否重传、接收方是否累计确认。

重复字节也有多种来源。原报文只是延迟，发送端先行重传后，两份副本都可能到达；网络设备也可能复制报文；抓包位置还可能让同一数据在不同阶段各被记录一次。接收 TCP 依据序列号识别已经接收的范围，只把连续且唯一的字节交给应用。

## 接收端怎样保存乱序数据

假设当前 `Ack = 2001`，说明 $[1001,2001)$ 已经连续到达。接收端愿意接收的窗口足够大，此时 Seq 3001 的 1000 字节到达。接收端可以把 $[3001,4001)$ 放进乱序队列，同时继续期待 Seq 2001。

应用读取位置受连续前缀约束。即使 $[3001,4001)$ 已经在内核内存中，应用也会先等 $[2001,3001)$ 补齐。缺口填满后，TCP 将拼接好的连续字节流按序交给应用。

累计 Ack 仍停在 2001。单靠这一字段，发送端只能知道“最左侧缺口仍存在”。SACK 选项补充报告缺口右侧已经收到的区间，使发送端形成更精确的记分板。

## SACK 的协商和区间语义

SACK 使用两个选项。`SACK Permitted` 只出现在 SYN 中；一端发送它，表示该端能够接收和处理未来的 SACK 选项。双方在各自 SYN 中都发送时，两个数据方向都具备使用条件。连接建立后，数据接收方可在 ACK 中携带 SACK Blocks。

每个 SACK Block 由两个 32 位序列号组成：

$$
[\text{Left Edge},\ \text{Right Edge})
$$

左边界是该连续块的第一个序列号，右边界是最后一个字节之后的序列号。右边界采用开区间，这与 Seq 和 Ack 的计算方式一致。SACK 选项长度为 $8n+2$ 字节，40 字节 TCP 选项空间理论上最多容纳 4 个块；Timestamp 等其他选项也占空间，常见报文可容纳的块数会减少。

SACK 报告属于补充信息，TCP 首部中的 Ack 继续表达累计确认。发送端通常保留数据，直到累计 Ack 越过对应范围。RFC 2018 还允许接收端在资源压力下撤回曾经报告的 SACK 信息，因此发送端恢复逻辑保留超时与累计确认这条稳健路径。

## 用数字画出缺口

仍以每段 1000 字节为例：

| 到达事件 | 接收端连续前缀 | 累计 Ack | SACK Blocks |
| --- | --- | --- | --- |
| A：$[1001,2001)$ | $[1001,2001)$ | 2001 | 空 |
| C：$[3001,4001)$ | $[1001,2001)$ | 2001 | $[3001,4001)$ |
| D：$[4001,5001)$ | $[1001,2001)$ | 2001 | $[3001,5001)$ |
| B：$[2001,3001)$ | $[1001,5001)$ | 5001 | 空 |

C 与 D 相邻，所以接收端把它们合并为一个 SACK Block。B 到达后，左侧缺口消失，累计 Ack 一步推进到 5001。

再看两个缺口。B：$[2001,3001)$ 与 D：$[4001,5001)$ 均缺失，A、C、E 已到达：

```text
已累计确认        缺口 B           已收到 C         缺口 D          已收到 E
[1001,2001)   [2001,3001)     [3001,4001)    [4001,5001)    [5001,6001)
Ack = 2001                     SACK 3001-4001                 SACK 5001-6001
```

发送端看到 `Ack = 2001` 与两个 SACK Block，便可优先恢复 B、D，已报告到达的 C、E 通常可跳过。RFC 6675 描述了基于 SACK 记分板估算在途数据并执行恢复的一套保守算法；具体内核还可能把它与 RACK 等机制组合。

### 重复数据与 DSACK

RFC 2883 定义了 Duplicate SACK。接收端可以用第一个 SACK Block 报告重复到达的序列范围。发送端由此获得“某次重传可能是多余的”这一反馈，并可调整乱序容忍或恢复统计。DSACK 依赖端点实现和抓包完整性，应用仍只接收一份有序字节。

## 怎样读 Wireshark 标签

Wireshark 按当前会话内已经看到的 Seq/Ack 推导标签：

- `TCP Out-Of-Order`：当前段的序列位置与分析器预测的下一位置有偏差；
- `TCP Dup ACK`：Ack 未推进，并满足分析器对重复确认的条件；
- `TCP Previous Segment Not Captured`：分析器看见序列缺口，名称已经提示捕获缺失这一可能性；
- `TCP Spurious Retransmission`：当前重复序列范围在分析器所见历史中似乎已被确认；
- `SACK`：线上 TCP 选项携带的真实区间，区间背后的丢失原因仍需推理。

判读时按四步进行：先验证捕获是否含三次握手，再检查 Seq 范围；随后用累计 Ack 和 SACK 画接收区间；最后比较缺口补齐时间、重传时间与另一端抓包。发送端的 `ss -ti`、重传计数和 RACK 状态可以补足算法证据。

## 从 SACK 记分板推导重传范围

可以把发送端尚未累计确认的序列空间画成方格。每收到一个 SACK Block，就给覆盖区间标上“接收端报告已到达”；累计 Ack 左侧标为“已完成”；两者之间仍空白的方格形成候选缺口。发送端算法还会考虑重复 ACK 数量、发送时间和重排容忍，因此候选缺口与立即重传之间存在一个判定阶段。

例如发送端已发出 $[1000,7000)$，当前 `Ack = 2000`，ACK 中带有 `[3000,5000)` 和 `[6000,7000)`：

| 序列范围 | 记分板状态 | 下一步含义 |
| --- | --- | --- |
| $[1000,2000)$ | 累计确认 | 可推进发送队列左边界 |
| $[2000,3000)$ | 空白缺口 | 候选恢复范围 |
| $[3000,5000)$ | SACK 已报告 | 接收端当前保存 |
| $[5000,6000)$ | 空白缺口 | 候选恢复范围 |
| $[6000,7000)$ | SACK 已报告 | 接收端当前保存 |

当 $[2000,3000)$ 补齐后，累计 Ack 可先推进到 5000；第二个缺口仍使 Ack 停住，`[6000,7000)` 继续通过 SACK 报告。等 $[5000,6000)$ 到达，累计 Ack 才能推进到 7000。这种阶梯变化可以直接从抓包逐帧复算。

SACK Block 数量受选项空间限制，某个 ACK 可能只列出接收队列的一部分。连续多份 ACK 的 SACK 并集可以回顾哪些区间曾被报告到达。历史并集只记录曾被报告的区间；最后一份 ACK 的有效状态以该帧 SACK 块为准，发送端同时保留处理 SACK 撤回的能力。分析报告应保留每帧原始块，再把历史并集作为辅助视图，便于识别 ACK 丢失和块更新。

双向传输需要建立两块独立记分板。客户端发送方向使用服务端返回的 Ack/SACK，服务端发送方向使用客户端返回的 Ack/SACK。按方向分别上色，再用四元组和时间戳关联，可避免把反向数据的序列号混入当前缺口。

## 受控实验：制造有限乱序

复用第20章建立的 `tcp-rx` 网络命名空间；若已在第20章末删除它，先重新执行该章的拓扑创建命令。随后确认接口存在：

```bash
ip link show veth-tx
sudo ip netns exec tcp-rx ip link show veth-rx
```

终端 A 启动服务端，终端 B 在接收端接口抓包：

```bash
sudo ip netns exec tcp-rx iperf3 -s -B 10.200.20.2
sudo ip netns exec tcp-rx tcpdump -i veth-rx -s 0 -w chapter21.pcap 'tcp port 5201'
```

终端 C 配置有抖动的延迟和有限乱序，再发送 32 MiB：

```bash
sudo tc qdisc replace dev veth-tx root netem delay 35ms 15ms reorder 25% 50%
sudo ip netns exec tcp-rx tc qdisc replace dev veth-rx root netem delay 35ms
iperf3 -c 10.200.20.2 -n 32M -l 1200 -i 0.5
```

在 Wireshark 中先选定一个 `tcp.stream`，再使用：

```text
tcp.stream == N &&
(tcp.analysis.out_of_order || tcp.analysis.duplicate_ack ||
 tcp.analysis.spurious_retransmission || tcp.options.sack.count > 0)
```

### 预期现象

1. 某些高 Seq 段先到，累计 Ack 暂停，ACK 中出现一个或多个 SACK Block。
2. 延迟段自行抵达时，累计 Ack 快速越过已缓存区间；发送端也可能先触发重传。
3. 传给应用的数据仍保持序列顺序，应用只累计每个序列位置的一份字节。
4. 卸载和聚合可能让本机抓包显示较大的 TCP 数据块。可在两个虚拟接口分别抓包，利用两侧结果理解抓包点差异。

结束后在服务端与抓包终端按 `Ctrl+C`，再移除规则；继续后续实验时保留命名空间：

```bash
sudo tc qdisc del dev veth-tx root
sudo ip netns exec tcp-rx tc qdisc del dev veth-rx root
```

若环境缺少 `netem`，可抓取自己控制的 Wi-Fi、VPN 或跨区域文件传输，先用 `tcp.options.sack.count > 0` 搜索自然发生的缺口。当前样本十分稳定时，可直接用本章数字表练习：遮住最后一列，只根据到达顺序填写 Ack 与 SACK，再与答案对照。

## 理解检查

1. `Ack = 7000, SACK = [9000,11000)` 表示哪段连续前缀已确认，当前最左缺口从哪里开始？
2. $[3000,4000)$ 与 $[4000,5000)$ 同时在接收队列中时，应形成几个 SACK Block？
3. 缺口自行补齐和缺口由重传补齐，在单侧抓包中可用哪些时间与序列证据区分？
4. 为什么发送端仍需等累计 Ack 推进后再释放对应重传数据？

## 小结

接收端用乱序队列保存窗口内的非连续数据，用累计 Ack 描述连续前缀，用 SACK Blocks 描述缺口之后的已到达区间。重复数据按序列范围去重，DSACK还能把重复情况反馈给发送端。Wireshark 标签提供检索入口，Seq/Ack/SACK 的区间推导才是可复核的分析主体。
