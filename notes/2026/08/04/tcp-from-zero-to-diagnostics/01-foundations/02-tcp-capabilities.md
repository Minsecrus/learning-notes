# 第2章 TCP 提供怎样的通信能力

IP 负责尽力把数据报送向目标。传输途中可能出现丢失、重复、乱序、比特差错和拥塞，通信双方的处理速度也可能相差很大。TCP 运行在两端主机中，通过连接状态、字节编号、确认、重传和窗口控制，把这些变化整理成应用可以顺序读写的双向字节流。

本章先画全景地图。每项机制的精确字段、算法和状态变化都会在后文展开。

## 先做一个预测

假设客户端调用一次 `sendall` 提交 2400 字节，服务端使用 `recv(700)` 读取。请预测：

1. 服务端会调用几次 `recv` 才累计得到 2400 字节？
2. Wireshark 会看到几个携带数据的 TCP 报文段？
3. 客户端的 `sendall` 返回时，服务端业务代码是否已经处理完数据？

第一个和第二个答案都受系统调度、缓冲区、MSS 与卸载机制影响，具体次数允许变化。第三个问题涉及证据层次：`sendall` 返回只表明 Python 已将全部字节交给本地 Socket 发送流程；远端业务结果需要应用响应来表达。

## 一个直觉模型 两卷带编号的纸带

可以把一条 TCP 连接想象成方向相反的两卷纸带：

- 客户端向服务端的纸带拥有自己的字节编号。
- 服务端向客户端的纸带也拥有自己的字节编号。
- 发送方可以把连续纸带裁成若干段交给 IP。
- 接收方按照编号拼回连续前缀，再交给应用读取。
- 确认号像一张回执，写着“下一次期待从哪个编号开始”。

这个模型同时表达了两个关键事实。TCP 是全双工的，两个方向可以同时传输；TCP 的编号对象是字节位置，报文段负责承载一段连续字节。

## 连接与端口

TCP 在端主机上维护连接状态。服务端通常在约定端口监听，客户端由操作系统分配临时端口。建立连接后，源 IP、源端口、目标 IP、目标端口组成四元组，在相应网络上下文中帮助系统找到正确连接。

端口解决“交给哪个 TCP 端点”的问题。到达同一服务器 IP 的 Web 请求可以发往 443，数据库连接可以发往另一个端口；同一服务端口也能同时接纳许多客户端，因为它们的四元组各不相同。

第4章会把监听 Socket、已连接 Socket 和四元组放到操作系统视角下观察。

## TCP 怎样整理一条字节流

### 序列号定位字节

发送方向中的每个字节都占据一个序列号位置。某个 TCP 报文段的 Seq 指向它所携带的第一个数据字节。假设相对 Seq 为 1000 的报文段携带 500 字节，那么它覆盖 `[1000, 1500)`，下一个连续字节的位置是 1500。

分段大小可以变化，同一范围也可能因重传再次出现。接收端依靠序列号判断连续、缺口、乱序和重复，而应用最终看到的是整理后的连续字节。

### 校验和发现传输差错

每个 TCP 报文段带有校验和，计算范围包含 TCP 首部、数据以及来自 IP 层的伪首部信息。接收端用它发现常见的传输比特差错，校验失败的报文段会被丢弃，发送端随后可通过丢包检测机制重传相应字节。

TCP 校验和属于差错检测机制。通信身份认证和抵御恶意篡改通常由 TLS 等密码学协议承担。

### 累计确认推进连续前缀

接收方通过 ACK 告诉发送方自己已经接收的连续进度。`Ack = 1500` 表示下一个期待的字节位置为 1500，也就是 1500 之前的连续序列空间已经得到确认。

当 1000～1499 到达、1500～1999 缺失、2000～2499 先到时，累计确认仍停在 1500。支持 SACK 的连接还可以额外报告“2000～2499 已在接收端”，让发送方更准确地修补缺口。

### 丢包检测与重传

发送方会保存尚未确认的数据，并测量往返时间。确认长时间保持原值时，重传计时器可以触发重传；连续确认同一缺口、SACK 信息和现代基于时间的算法也能提供更早的丢包线索。

重传有一个重要效果：应用继续按照原顺序读取字节。网络中可以出现多个副本，接收 TCP 会根据序列空间保留需要的内容并处理重复部分。

第20章会讨论 RTO、重复 ACK、快速重传与 RACK-TLP，第21章会讨论乱序和 SACK。

## 两种窗口解决两种速度问题

### 接收窗口照顾接收端

接收应用可能读取缓慢。接收 TCP 用接收窗口 `rwnd` 告诉发送方，当前还愿意接收多少序列空间。缓冲区逐渐占满时，窗口缩小；应用读走数据后，窗口可以再次扩大。

这属于流量控制，目标是让快速发送方适应较慢接收方。第22章会观察零窗口、窗口更新和探测。

### 拥塞窗口照顾网络路径

即使接收端空间充足，路径中的链路和路由器容量仍然有限。发送方维护拥塞窗口 `cwnd`，根据确认、丢包、ECN 和所用拥塞控制算法调整在途数据规模。

实际可发送的在途数据通常同时受 `rwnd` 与 `cwnd` 限制，还受应用供数速度、发送缓冲区和实现策略影响。可以先记住一个简化关系：

$$
\text{可用发送空间} \lesssim \max\!\left(0,\ \min(\text{rwnd},\ \text{cwnd}) - \text{在途未确认数据}\right)
$$

第23章会展开慢启动、拥塞避免、CUBIC 与 BBR 等思路。

## TCP 能力地图

| 应用看到的能力 | 主要 TCP 机制 | 观察线索 |
| --- | --- | --- |
| 双向同时传输 | 两个独立序列空间与发送、接收状态 | 双向 Seq、Ack 都在推进 |
| 按序读取字节 | 序列号、乱序队列、累计确认 | 线上顺序与应用读取顺序可能有差异 |
| 修复可恢复的丢失 | 未确认数据、计时器、重传、SACK | ACK 停顿、SACK、重传报文 |
| 处理重复数据 | 序列空间与接收状态 | 同一序列范围在线上重复出现 |
| 适应接收端速度 | `rwnd` 与窗口更新 | Window 缩小、归零、恢复 |
| 适应路径容量 | `cwnd`、拥塞信号与发送节奏 | 在途规模和吞吐随时间变化 |
| 发现常见传输差错 | TCP Checksum | 校验结果与后续重传 |

这些机制共同维持连接内的有序可靠字节流。连接故障、路径长期中断或主机状态丢失时，Socket 最终会向应用报告错误或超时，应用据此决定恢复策略。

## 可靠交付停在哪一层

理解 ACK 的含义非常重要。服务端发出的 TCP ACK 表示相应连续字节已经进入服务端 TCP 的接收状态。以下应用事实仍需应用响应、日志或持久化记录来证明：

- 服务端进程已经调用 `recv` 读到这些字节。
- 请求格式已经通过校验。
- 数据已经持久化到数据库。
- 业务操作已经成功完成。

这些事实由应用协议表达。例如客户端发送带请求 ID 的“创建订单”消息，服务端完成事务后返回“请求 42 已提交”。客户端以这条应用响应判断业务结果。若响应在途中丢失，重试策略还要结合请求 ID 和幂等规则。第26、27章会系统处理这类问题。

同样地，本地 `send` 返回表示本地内核接受了相应字节数，数据随后可能仍位于发送缓冲区、网卡队列或网络路径中。应用可以通过响应协议确认更高层结果。

## 实验 比较写入、读取与报文长度

将下面代码分别保存为 `capability_server.py` 和 `capability_client.py`。

服务端：

```python
import socket
import time

HOST = "127.0.0.1"
PORT = 9012

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as listener:
    listener.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    listener.bind((HOST, PORT))
    listener.listen()
    print(f"listening on {HOST}:{PORT}")

    conn, peer = listener.accept()
    with conn:
        print(f"accepted {peer}; pause 2 seconds")
        time.sleep(2)
        total = 0
        while True:
            chunk = conn.recv(700)
            if chunk == b"":
                break
            total += len(chunk)
            print(f"recv returned {len(chunk)} bytes; total={total}")

        response = f"RECEIVED {total}".encode("ascii")
        conn.sendall(response)
        print(f"application response: {response!r}")
```

客户端：

```python
import socket

HOST = "127.0.0.1"
PORT = 9012
payload = b"A" * 1200 + b"B" * 1200

with socket.create_connection((HOST, PORT)) as sock:
    print(f"local={sock.getsockname()} peer={sock.getpeername()}")
    sock.sendall(payload)
    print(f"sendall accepted {len(payload)} bytes locally")
    sock.shutdown(socket.SHUT_WR)

    parts = []
    while True:
        chunk = sock.recv(4096)
        if chunk == b"":
            break
        parts.append(chunk)
    print(f"application response: {b''.join(parts)!r}")
```

实验步骤：

1. 在 Wireshark 的回环接口开始捕获，显示过滤器设为 `tcp.port == 9012`。
2. 在 PowerShell 窗口 A 运行 `python .\capability_server.py`。
3. 在窗口 B 运行 `python .\capability_client.py`。
4. 服务端暂停的两秒内，在窗口 C 运行 `Get-NetTCPConnection | Where-Object LocalPort -eq 9012`。
5. 保存抓包，并用 `tcp.port == 9012 && tcp.len > 0` 查看携带数据的报文段。

### 预期现象与解释

客户端始终提交 2400 字节。服务端每次 `recv(700)` 返回最多 700 字节，累计结果应为 2400；每次具体返回长度和调用次数允许随运行变化。最终 `RECEIVED 2400` 是本实验定义的应用层确认。

Wireshark 中每个 `tcp.len` 是抓包观察到的 TCP 数据长度。它与 `sendall` 以及 `recv` 日志通常呈现不同分组。回环抓包和网卡卸载还可能让单个报文显示得很大。比较时关注总字节范围、方向和 Seq 推进，并将每个工具的观察层次写入记录。

## 把结论说精确

- TCP 保留字节顺序，应用自行定义消息边界。
- TCP ACK 记录接收端 TCP 的连续接收进度，业务结果由应用响应表达。
- TCP 的可靠性依托正在维护的连接状态；应用仍会处理错误、超时和重试。
- 接收窗口反映接收 TCP 的可用序列空间，业务队列容量由应用单独管理。
- 加密、身份认证、消息格式和操作幂等性由 TLS 与应用协议补充。

## 本章小结

TCP 通过端点状态组织连接，用序列号定位字节，用累计确认和重传修补缺口，用接收窗口适应接收方，用拥塞窗口适应网络路径，并为两个方向分别维护状态。应用由此得到有序、可靠的全双工字节流，同时继续负责消息格式、业务结果、超时策略与安全语义。
