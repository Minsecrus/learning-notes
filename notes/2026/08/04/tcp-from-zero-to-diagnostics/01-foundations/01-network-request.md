# 第1章 一次网络请求是怎样发生的

在浏览器地址栏输入 `https://example.com/learn?id=7` 并按下回车后，屏幕往往很快出现页面。短短几百毫秒里，计算机完成了名称解析、路径选择、局域网交付、TCP 建连、TLS 协商以及 HTTP 交换。理解这条链路，会为后续所有 TCP 字段建立位置感。

## 先做一个预测

请先凭直觉排列下面这些事件：

- 查询域名对应的 IP 地址
- 选择出口接口和下一跳
- 在需要时解析下一跳的链路层地址
- 建立 TCP 连接
- 发送 HTTP 请求
- 协商 TLS 加密参数
- 读取 HTTP 响应

针对目标站点的一条新 HTTPS 连接，常见逻辑顺序是：DNS → 路由选择 → 必要时执行 ARP 或 IPv6 ND → TCP → TLS → HTTP。若 DNS 解析需要在线查询，DNS 查询本身也会经历路由选择和链路交付；这里的顺序聚焦于取得目标站点候选 IP 之后的连接过程。缓存、既有连接或代理也可能让部分步骤直接复用已有结果。

## 第一步 解析 URL

URL 是应用层对资源位置的描述。以 `https://example.com/learn?id=7` 为例：

| 部分 | 值 | 作用 |
| --- | --- | --- |
| 方案 | `https` | 选择 HTTPS 语义，默认目标端口为 443 |
| 主机名 | `example.com` | 交给名称解析系统寻找地址 |
| 路径 | `/learn` | 告诉 HTTP 服务希望访问哪个资源 |
| 查询参数 | `id=7` | 携带应用层参数 |

主机名仍是给人和应用使用的名称。发送 IP 数据报需要目标 IP，因此客户端接下来执行名称解析。显式写在 URL 中的 `:8443` 会覆盖方案的默认端口。

## 第二步 由 DNS 得到候选 IP

DNS 解析器会寻找主机名的地址记录。IPv4 地址通常来自 A 记录，IPv6 地址通常来自 AAAA 记录。应用可能得到多个候选地址，再根据系统策略、地址可达性与连接进展选择其中一个。

实际查询路径可能经过浏览器缓存、操作系统缓存、本地递归解析器和上游 DNS 服务。缓存命中时，线上抓包中可以直接进入后续步骤。这个现象本身就是一条证据：一次抓包只记录捕获期间经过该观察点的流量。

DNS 回答“这个名字有哪些地址”。端口来自 URL、协议默认值或应用配置。两者合在一起，形成 TCP 尝试连接的远端地址，可以记作 `<解析所得 IP>:443`。具体地址会随网络与解析时间变化，实验时以本机输出为准。

## 第三步 选择路由与下一跳

操作系统拿到目标 IP 后，会在路由表中寻找最匹配的目标前缀，进而确定三项内容：

1. 从哪个网络接口发出。
2. 使用哪个本地源 IP。
3. 下一跳是目标主机本身，还是路由器。

同一局域网内的目标通常可以直接作为下一跳。跨网段目标通常先交给默认网关。路由器收到 IP 数据报后继续查自己的路由表，一跳一跳将数据送向目的网络。

这里出现两个作用范围不同的地址：IP 地址用于跨网络的端到端寻址；链路层地址用于当前一跳的交付。以常见以太网为例，发送帧需要下一跳的 MAC 地址。IPv4 主机通过 ARP 查询下一跳 IPv4 地址对应的 MAC 地址；IPv6 使用基于 ICMPv6 的 Neighbor Discovery。

访问公网服务器时，本机以太网帧的目标 MAC 通常属于家庭路由器或企业网关。每经过一个路由器，链路层首部都会针对新的一跳重新生成，IP 目标地址继续指向最终服务器。

## 第四步 建立 TCP 连接

客户端已经掌握目标 IP 和端口，便可以请求操作系统建立 TCP 连接。操作系统为本端选择源 IP 和临时源端口，随后交换 SYN、SYN+ACK、ACK，协商初始序列号以及 MSS、窗口缩放、SACK 等能力。

例如，一次连接可由下面四项标识：

```text
客户端 IP:临时端口  ->  服务器 IP:443
```

两端各有独立的发送方向。握手完成后，客户端和服务端都拥有发送与接收字节的状态。三次握手的每个 Seq、Ack 计算会在第15章完整展开。

## 第五步 在 TCP 上建立 TLS

HTTPS 会在 TCP 字节流中交换 TLS 握手消息。双方协商协议版本和密码套件，客户端验证服务器证书，双方建立后续加密所需的密钥。此后 HTTP 请求与响应以加密形式承载在 TLS Record 中。

抓包者通常仍可看到 IP、TCP 首部和 TLS Record 的长度、方向与时间，HTTP 路径、首部和正文则受到加密保护。第30章会详细区分应用消息、TLS Record 与 TCP 报文段的边界。

## 第六步 交换 HTTP 请求与响应

TLS 通道可用后，客户端把 HTTP 请求字节写入连接。服务端 HTTP 组件解析请求，将其交给应用处理，再把状态码、响应首部和正文写回连接。客户端读取响应字节，完成 HTTP 解析，浏览器随后还可能为 HTML 引用的脚本、样式表、图片和字体发起更多请求。

HTTP/1.1 可以复用一条 TCP 连接处理后续请求。HTTP/2 也运行在 TCP 上，并在一条连接中复用多条流。HTTP/3 运行在 QUIC 上，底层使用 UDP。浏览器现场抓包可能同时出现这些形态，所以本教程的初次外网实验用 curl 明确选择 HTTP/1.1。

## 封装与解封装

发送端每一层都把上层内容当作自己的载荷，并加上本层控制信息。下面的嵌套图表达概念上的承载关系：

```text
HTTP 请求字节
└─ TLS Record（HTTPS 场景）
   └─ TCP 首部 + TCP 数据
      └─ IP 首部 + IP 数据
         └─ 链路层首部 + 链路层载荷 + 校验信息
```

各层边界没有固定的一一对应关系。一条 TLS Record 可以跨越多个 TCP 报文段，一个 TCP 报文段也可以承载多条相邻 Record 的字节；链路和 IP 层同样按各自规则封装当前载荷。

接收端沿相反方向处理：网卡接收当前链路上的帧，IP 层根据 IPv4 Protocol 字段或 IPv6 Next Header 字段把载荷交给 TCP，TCP 根据连接状态重组有序字节，TLS 解密，HTTP 解析应用消息。

同一批应用字节在不同层有不同名称。应用看到请求，TCP 处理字节序列和报文段，IP 转发数据报，链路层在一跳范围内传输帧。Wi-Fi、以太网和回环接口的链路层形式也会有所不同。

```mermaid
flowchart LR
    A["应用：URL 与 HTTP"] --> B["传输：TCP 连接与字节流"]
    B --> C["网络：IP 地址与路由"]
    C --> D["链路：下一跳与帧"]
    D --> E["路由器或目标主机"]
```

## 四种标识各管一段范围

| 标识 | 解决的问题 | 常见观察位置 |
| --- | --- | --- |
| 域名 | 人和应用怎样稳定引用服务 | URL、DNS 查询 |
| IP 地址 | 数据报跨网络送往哪台主机或接口 | IP 首部、路由表 |
| MAC 地址 | 当前链路上的帧交给哪个下一跳 | 以太网首部、邻居表 |
| TCP 端口 | 到达主机后交给哪个 TCP 端点 | TCP 首部、Socket 状态 |

Socket 是应用使用网络能力的操作系统接口。连接建立后，一个已连接 Socket 关联本地地址与端口、远端地址与端口以及 TCP 状态。第4章会从操作系统视角继续展开。

## 实验 对齐 DNS、连接与请求

本实验访问为文档示例保留的 `example.com`。先在 Wireshark 中选择实际联网接口并开始捕获，设置显示过滤器：

```text
dns || tcp.port == 443
```

然后在 PowerShell 中依次运行：

```powershell
Resolve-DnsName example.com -Type A -DnsOnly
Resolve-DnsName example.com -Type AAAA -DnsOnly
Test-NetConnection example.com -Port 443 -InformationLevel Detailed
curl.exe --noproxy "*" --http1.1 -v https://example.com/ --output NUL
route print
Get-NetNeighbor | Sort-Object InterfaceIndex,IPAddress
```

企业网络有时要求显式代理。此时按网络策略使用代理，并把代理地址记录为 TCP 的实际远端。`curl -v` 会显示真正连接的地址，`Test-NetConnection` 会显示测试时选择的远端地址。

### 预期现象

- `Resolve-DnsName` 给出一个或多个候选地址。
- `Test-NetConnection` 显示源地址、远端地址、接口与端口连通结果。
- curl 输出中先出现连接与 TLS 信息，随后出现 HTTP 请求行和响应状态。
- Wireshark 中可看到 TCP 握手、TLS 交换、加密应用数据与连接关闭。
- 邻居表里常见的是本地网关或同链路主机；公网服务器的 MAC 映射通常位于远端网络。

DNS 报文也可能因缓存、加密 DNS 或 VPN 路径而缺席。把这个差异写入实验记录，再以 `Resolve-DnsName` 输出和 curl 实际连接地址补齐证据。若 curl 复用了其他机制，命令行中的 `--http1.1` 会把应用协议限定为经 TCP 承载的 HTTP/1.1。

## 协议模型的适用条件

本章用“首次访问、需要新连接”的路线建立模型。真实浏览器还会使用 DNS 缓存、连接池、TLS 会话恢复、代理、CDN 和 Happy Eyeballs 等机制。它也可能优先选择 HTTP/3。分析现场时，可以先找实际使用的远端 IP、传输协议和连接复用情况，再将观察结果套入对应路线。

相关的链路层背景可继续阅读[Frame、MAC、IP 与 ARP](../../../../05/24/networking-frame-mac-ip.md)，Socket 术语可参考[Socket 与 WebSocket](../../../../05/24/networking-socket-websocket.md)。

## 理解检查

1. URL 中哪一部分参与 DNS 查询，哪一部分通常决定目标端口？
2. 访问公网服务器时，本机发出的以太网帧通常以谁的 MAC 地址为目标？
3. 路由表负责确定哪三项发送信息？
4. HTTPS 抓包为何仍能看到 TCP 首部，同时难以直接读取 HTTP 正文？
5. 抓包中缺少 DNS 查询时，可以从哪些证据继续确认目标地址？

## 本章小结

一次网络请求是一条逐层收敛的路径：URL 给出应用意图，DNS 提供候选 IP，路由表选择接口和下一跳，ARP 或 IPv6 ND 提供当前链路地址，TCP 建立双向字节流，TLS 保护其上的通信，HTTP 表达请求与响应。域名、IP、MAC 和端口分别服务于不同范围，组合起来才让数据抵达正确应用。

下一章会聚焦其中的 TCP 层，回答它怎样在会丢包、乱序和拥塞的 IP 网络上维护一条有序字节流。
