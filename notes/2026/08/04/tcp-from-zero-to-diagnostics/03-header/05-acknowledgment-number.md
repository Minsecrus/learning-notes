# 第11章 Acknowledgment Number：累计确认

上一章给每个字节安排了序列号。本章站到接收方一侧，回答一个更关键的问题：接收方怎样用一个 32 位数字告诉发送方，连续字节流已经推进到了哪里。

## 先把 Ack 读成一句完整的话

当报文段的 ACK 标志为 1 时，Acknowledgment Number 才具有确认语义。设报文中的确认号为 $X$，它表达：

> 我期待你接下来发送序列号为 $X$ 的字节；在此之前的连续序列空间已经得到确认。

因此，`Ack = X` 指向“下一个期待的位置”。用左闭右开的区间表示，接收方已经连续接收的范围可写成 $[起点, X)$。右端点 $X$ 本身仍在期待之中。

举例：客户端发送一个 `Seq = 1001, TCP Len = 400` 的报文段。数据占用序列号 $[1001, 1401)$，服务端收齐后可以回复 `Ack = 1401`。发送方看到该值，便知道序列号小于 1401 的这段连续前缀已经得到确认。

回到第三篇共用的 `HELLO TCP\n` 样本：报文为 `Seq = 0x6a1b2c3e, Len = 10`，所以服务端连续收到它后应期待：

$$
\mathtt{0x6a1b2c3e}+10=\mathtt{0x6a1b2c48}
$$

反向报文可用 `Ack = 0x6a1b2c48` 确认这 10 字节。样本本身还携带 `Ack = 0x10203041`，它同时说明客户端正在期待服务端发送方向的 `0x10203041`。一条数据报文由此同时推进本端 Seq 空间，并汇报反方向 Ack 空间。

TCP 连接有两个独立的序列号空间。一个报文里的 `Seq` 描述本端发送方向，`Ack` 描述对端发送方向。阅读双向抓包时，可以把它们读成两句话：

- `Seq = 3001, Len = 5`：本端发送从 3001 开始的 5 个字节；
- `Ack = 9013`：本端同时期待对方从 9013 继续发送。

这也解释了为何同一个报文可以同时携带数据和确认信息。TCP 的两个方向各自推进，ACK 常常随反向数据一同发送，这种做法称为捎带确认。

## 累计确认关注连续前缀

假设服务端当前期待 `Seq = 1401`，随后出现以下到达顺序：

| 到达次序 | 收到的数据区间 | 当前连续范围 | 可发送的累计 Ack |
| --- | --- | --- | --- |
| 1 | $[1701,1901)$ | 仍停在 1401 | 1401 |
| 2 | $[1401,1701)$ | 已连成 $[1401,1901)$ | 1901 |

第一批 200 字节位于更靠后的位置，前方仍有 300 字节缺口。接收 TCP 可以暂存这批乱序数据，同时保持 `Ack = 1401`。缺口到达后，两块数据连成连续前缀，确认号一次跃迁到 1901。

这就是“累计”的含义：一个较大的 Ack 同时覆盖此前连续范围中的全部字节。接收方可以用一次 `Ack = 1901` 覆盖多个报文段；Delayed ACK、捎带确认和调度时机都会减少线上纯 ACK 的数量。确认进度仍由 Ack 的数值表达，报文段数量不参与计算。

启用 SACK 后，第一步还可能携带 `SACK = [1701,1901)`，用于补充说明接收方已经暂存的后续区间。累计 Ack 继续停在 1401，SACK 则描述连续前缀之外的“数据岛”。第 14 章会完整解释这两个选项。

## SYN、FIN 和纯 ACK 怎样参与计算

数据字节、SYN、FIN 会占用序列空间。对起始序列号为 $S$、TCP 数据长度为 $L$ 的报文段，下一个位置为：

$$
S_{next} = S + L + I_{SYN} + I_{FIN} \pmod {2^{32}}
$$

其中，标志存在时对应的指示量 $I$ 取 1，其余情况取 0。ACK、PSH、RST、URG、ECE、CWR 和 AE 都不额外推进序列号。

用一组原始序列号完成整个推理：

| 方向 | Flags | Seq | TCP Len | Ack | 推理 |
| --- | --- | ---: | ---: | ---: | --- |
| 客户端 → 服务端 | SYN | 3000 | 0 | — | SYN 占用位置 3000 |
| 服务端 → 客户端 | SYN, ACK | 9000 | 0 | 3001 | 服务端期待客户端的 3001 |
| 客户端 → 服务端 | ACK | 3001 | 0 | 9001 | 客户端期待服务端的 9001 |
| 客户端 → 服务端 | ACK, PSH | 3001 | 5 | 9001 | 数据为 $[3001,3006)$ |
| 服务端 → 客户端 | ACK, PSH | 9001 | 12 | 3006 | 同时确认客户端的 5 字节 |
| 客户端 → 服务端 | ACK | 3006 | 0 | 9013 | 确认服务端的 12 字节 |

第三行和最后一行都是纯 ACK。它们携带当前 Seq，却不消耗新的序列号位置。若本端暂时没有发送数据，多个纯 ACK 可以使用相同的 Seq。纯 ACK 自身丢失时，TCP 通常依靠后续 ACK、反向数据或发送方重传继续推进状态。

FIN 的确认方式与 SYN 相同。若服务端发送 `Seq = 9013, Len = 20, FIN = 1`，数据占用 $[9013,9033)$，FIN 再占一个位置，对端收齐后的 Ack 为 9034。

## 一套稳定的逐帧手算方法

面对较长抓包，可以为两个方向各建一行账本：

| 发送方向 | 下一个期待位置 | 已暂存的后续区间 | 最近看到的对端 Ack |
| --- | ---: | --- | ---: |
| 客户端 → 服务端 |  |  |  |
| 服务端 → 客户端 |  |  |  |

每读取一个报文段，按以下顺序更新：

1. 先根据源、目标四元组确定发送方向；
2. 用 `tcp.len + SYN + FIN` 计算本段占用的序列空间；
3. 本段恰好从期待位置开始时，把连续右边界向前推进；本段位于更后方时，先记入暂存区间；
4. 把报文中的 Ack 与反方向账本的连续右边界比较；
5. 重传与重叠区间只补充覆盖证据，已经计入的字节保持原有进度；
6. 接近 `0xffffffff` 时对 $2^{32}$ 取模。

这张双向账本还能发现抓包缺帧：某个 Ack 突然跨过当前捕获中从未出现的区间，说明接收端已经见过那些字节，而当前抓包点或捕获过程缺少相应报文。此时应把“线上确认事实”和“本地捕获完整性”分别记录。

## TCP 确认与业务结果处在不同层次

累计 Ack 记录对端 TCP 的连续接收进度。应用读取、解析、写入数据库、调用下游服务和提交事务发生在后续层次。一个清晰的请求时间线可以写成：

1. 客户端发送 500 字节请求；
2. 服务端 TCP 接收连续字节并回复累计 Ack；
3. 服务端进程从 Socket 读取请求；
4. 应用发现字段校验失败；
5. 服务端发送业务错误响应，例如 `422 Unprocessable Content`。

第 2 步证明请求字节已经到达服务端 TCP 接收路径。第 5 步才表达本次业务处理结果。需要持久化语义的系统还会设计请求 ID、提交状态和应用层确认；客户端据此区分“传输已确认”“请求已受理”“事务已提交”等阶段。

因此，抓包中看到完整请求及其 TCP ACK，可以确认传输层进度。业务成功仍需结合响应、应用日志和持久化记录。主机随后崩溃、进程退出或事务回滚时，这些证据层会给出不同结论。

## 受控实验：从抓包手算 Ack

在 Windows 上选择 **Npcap Loopback Adapter** 抓包，并使用端口 39011。终端 A 启动一次性服务端：

```powershell
python -c "import socket,time; l=socket.socket(); l.bind(('127.0.0.1',39011)); l.listen(1); c,_=l.accept(); f=c.makefile('rb'); time.sleep(1); d=f.read(700); f.close(); print('server bytes:',len(d)); c.sendall(b'OK'); c.close(); l.close()"
```

终端 B 分两次写入共 700 字节：

```powershell
python -c "import socket,time; c=socket.create_connection(('127.0.0.1',39011)); c.sendall(b'A'*400); time.sleep(0.2); c.sendall(b'B'*300); f=c.makefile('rb'); print(f.read(2)); f.close(); c.close()"
```

停止抓包后使用显示过滤器：

```text
tcp.port == 39011
```

给分组列表添加 `tcp.seq`、`tcp.ack`、`tcp.len` 和 `tcp.flags` 列，然后完成以下记录：

1. 找到客户端 SYN，记下它的原始 Seq；服务端 SYN+ACK 的 Ack 应为该值加 1。
2. 找到携带 400 字节与 300 字节的范围。实际分段可能受到缓冲、调度和卸载影响，应以捕获到的 `tcp.len` 逐段相加。
3. 对每个服务端报文，计算“当前已连续接收范围的右端点”，再与 Ack 对照。
4. 观察服务端的 `OK` 是否同时携带对客户端数据的确认。
5. 在 Wireshark 的 TCP 协议设置中切换相对序列号显示，再比较原始值。两种显示只改变基准，差值和区间保持一致。

在典型结果中，700 字节可能形成一个、两个或更多 TCP 数据报文段；服务端也可能使用独立 ACK 或随 `OK` 捎带确认。稳定的观察是：确认号按连续收到的序列空间推进，推进量等于新接入连续前缀的数据长度，并计入 SYN、FIN 各自占用的一个位置。

## 理解检查

1. 当前期待值为 8001，随后连续收到 `Seq = 8001, Len = 600`。新的累计 Ack 是多少？
2. 当前 Ack 为 8601，先收到区间 $[9001,9301)$。此时累计 Ack 应停在哪里？
3. 客户端已经看见服务端对完整请求的 TCP ACK，随后等待业务响应超时。此刻可以确认哪一层事实？
4. `Seq = 12000, Len = 80, FIN = 1` 的报文完整到达后，对端应确认到哪个位置？

<details>
<summary>参考答案</summary>

1. `Ack = 8601`。
2. `Ack = 8601`；$[8601,9001)$ 仍是连续前缀前方的缺口。启用 SACK 时可另行报告 $[9001,9301)$。
3. 可以确认请求的连续字节已经到达对端 TCP；应用读取、处理和提交状态需要响应、日志或业务查询补充。
4. 数据推进 80，FIN 再推进 1，因此 `Ack = 12081`。

## 本章小结

- Ack 指向对方下一个期待的序列号，覆盖此前连续序列空间。
- 乱序数据可以先进入接收队列；累计 Ack 等待最前方缺口补齐，SACK 可补充报告后续数据岛。
- ACK 与纯 ACK 都不占序列空间，SYN、FIN 各占一个位置。
- 一个报文中的 Seq 与 Ack 分别描述两个发送方向，数据与确认可以同行。
- TCP ACK 证明对端 TCP 的接收进度；业务响应、日志和持久化状态继续描述应用处理结果。
- 手算时先画半开区间，再把数据长度、SYN 和 FIN 依次加入右端点。

## 规范依据

- [RFC 9293：Transmission Control Protocol (TCP)](https://www.rfc-editor.org/rfc/rfc9293.html)，定义 Acknowledgment Number、累计确认、序列空间以及 SYN/FIN 的占位规则。
