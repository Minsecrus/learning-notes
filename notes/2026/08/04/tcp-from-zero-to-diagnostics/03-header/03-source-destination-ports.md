# 第9章 源端口和目标端口

IP 地址把数据报送到一台主机，端口继续把 TCP 报文段送入主机中的通信端点。样本 TCP 首部的前四字节已经给出方向：

```text
c0 00 23 28
└───┘ └───┘
 源端口 目标端口
```

本章从这四个字节出发，解释操作系统如何在一个监听 Socket 与许多已连接 Socket 之间完成查找。

## 两个 16 位整数

源端口和目标端口各占 16 位，取值空间为 0～65535。样本采用网络字节序：

$$
\begin{aligned}
\text{Source Port}
  &=0xc000\\
  &=0xc0\times256+0x00\\
  &=192\times256\\
  &=49152
\end{aligned}
$$

$$
\begin{aligned}
\text{Destination Port}
  &=0x2328\\
  &=0x23\times256+0x28\\
  &=35\times256+40\\
  &=9000
\end{aligned}
$$

再结合 IPv4 首部中的地址，可以写出这条报文的方向：

```text
192.0.2.10:49152  ->  198.51.100.20:9000
```

服务端响应时，源和目标角色交换：

```text
198.51.100.20:9000  ->  192.0.2.10:49152
```

一来一回属于同一条连接。分析工具会把两个方向归入同一个 `tcp.stream`。

## 为什么连接需要四元组

设想服务端在 `198.51.100.20:9000` 上同时服务两个客户端：

| 连接 | 客户端端点 | 服务端端点 | 四元组 |
| --- | --- | --- | --- |
| A | `192.0.2.10:49152` | `198.51.100.20:9000` | `192.0.2.10, 49152, 198.51.100.20, 9000` |
| B | `192.0.2.11:53000` | `198.51.100.20:9000` | `192.0.2.11, 53000, 198.51.100.20, 9000` |

两条连接共享服务端端口 `9000`，客户端地址与端口让四元组保持唯一。操作系统可以据此维护两套独立状态：各自的 Seq、Ack、接收窗口、重传计时器和缓冲区。

工程实践中还会把 IP 版本、传输协议与网络命名空间放进查找上下文。这样，IPv4/TCP、IPv6/TCP 以及彼此隔离的容器网络都能维护各自的端点集合。“四元组”仍是阅读单条 TCP 连接最实用的核心标识，系统上下文则说明它在哪一张连接表中生效。

若同一台客户端进程再次连接同一服务端，操作系统通常再分配一个临时端口：

```text
127.0.0.1:49152 -> 127.0.0.1:9000
127.0.0.1:49153 -> 127.0.0.1:9000
```

这两个连接可以由同一客户端进程创建，也可以来自两个进程。端口属于传输层端点命名空间；进程、线程与 Socket 的对应关系由操作系统和应用架构管理。一个进程可持有许多 Socket，多个工作进程也可在系统提供的端口复用机制下共同承接流量。

## 监听端点与已连接端点

服务端通常经历两个层次：

1. 监听 Socket 绑定本地地址和本地端口，例如 `0.0.0.0:9000`。
2. 握手完成后，内核为每条连接维护包含远端信息的已连接状态；应用通过 `accept` 取得对应的已连接 Socket。

通配地址 `0.0.0.0` 表示在符合系统规则的本机 IPv4 地址上接收连接，IPv6 中的 `::` 承担相应的通配绑定角色。若服务端只绑定 `127.0.0.1:9000`，回环流量可以匹配该监听端点；发往局域网地址的流量会走另一套本地地址匹配条件。

对一个到达的 TCP 报文段，可以采用下面的概念模型理解内核查找：

```text
报文到达
  ↓
读取协议、目标地址、目标端口、源地址、源端口
  ↓
按完整连接标识查找已连接状态
  ↓
若报文用于建立新连接，再按本地地址与端口查找监听端点
  ↓
进入该连接或监听路径的队列与状态机
```

实际内核常使用哈希表、网络命名空间、接口约束与端口复用规则提高查找效率。上面的模型保留了抓包诊断最重要的两点：已建立连接依赖双方端点；监听入口主要围绕本地端点组织。

一个常见观察是：`Get-NetTCPConnection` 或 `ss` 会同时列出一行 `LISTEN` 和多行 `ESTABLISHED`。它们可以共享本地端口 `9000`，同时具有不同的状态与远端端点。

## 端口号的常用分区

IANA 的服务名与端口号注册体系常把端口空间描述为：

| 范围 | 常见名称 | 阅读抓包时的用途 |
| ---: | --- | --- |
| 0～1023 | System / Well-Known Ports | 常见基础服务注册范围 |
| 1024～49151 | User / Registered Ports | 注册应用服务范围 |
| 49152～65535 | Dynamic / Private Ports | 常见客户端动态选择范围 |

样本客户端端口 `49152` 位于 Dynamic/Private 范围，服务端实验端口 `9000` 位于 User 范围。操作系统的临时端口分配范围可配置，各平台实际范围与策略也会变化。抓包中出现高端口时，可以把“客户端临时端口”作为初始假设，再结合握手方向、监听状态和应用日志验证。

端口 `0` 还常用于 Socket API 的特殊请求：应用绑定本地端口 0 时，操作系统可以自动选择一个可用端口。真正建立连接后，`getsockname()` 或系统连接表会给出最终分配值。

## 两个方向如何共同标识一条流

在客户端发出的报文中：

```text
src = 192.0.2.10:49152
dst = 198.51.100.20:9000
```

在服务端响应报文中：

```text
src = 198.51.100.20:9000
dst = 192.0.2.10:49152
```

分析同一连接时，可以把端点对视为无方向的集合；分析单条报文时，Source 与 Destination 始终携带清晰方向。Wireshark 显示过滤器也体现了这种差别：

```text
tcp.port == 9000
```

匹配源端口或目标端口为 9000 的两个方向；

```text
tcp.dstport == 9000
```

只匹配当前报文目标端口为 9000 的方向；

```text
ip.src == 192.0.2.10 && tcp.srcport == 49152 &&
ip.dst == 198.51.100.20 && tcp.dstport == 9000
```

匹配样本的单一发送方向。确定一条连接后，`tcp.stream == N` 通常最适合追踪该连接的双向报文，其中 `N` 替换为 Wireshark 分配的流编号。

## NAT 会改写抓包中的四元组

客户端位于私有网络时，NAT 设备可能把出站端点转换成公网端点。例如：

```text
NAT 内侧抓包：192.168.1.20:49152 -> 198.51.100.20:9000
NAT 外侧抓包：203.0.113.9:62001 -> 198.51.100.20:9000
```

NAT 维护映射状态，让返回方向的：

```text
198.51.100.20:9000 -> 203.0.113.9:62001
```

重新送往内侧的 `192.168.1.20:49152`。因此服务端看到的客户端端点是 `203.0.113.9:62001`，客户端本机 Socket 看到的是 `192.168.1.20:49152`。两侧抓包都忠实记录各自抓包点经过的报文。

故障分析时应先记录抓包位置，再比较地址转换表、负载均衡日志或代理日志。第36章会把 NAT、防火墙与负载均衡路径展开成多段连接模型。

## 实验：观察两个客户端共享服务端端口

### 准备与步骤

1. 打开第二篇的客户端与服务端代码，将两端的 `PORT` 常量从 `50007` 同步设为 `9000`；随后启动服务端，让它监听 `127.0.0.1:9000`，并在接受连接后保持一段时间。
2. 打开两个 PowerShell 窗口，分别启动客户端并连接该服务端。
3. 在第三个 PowerShell 窗口运行：

```powershell
Get-NetTCPConnection -State Established |
  Where-Object { $_.LocalPort -eq 9000 -or $_.RemotePort -eq 9000 } |
  Sort-Object LocalAddress, LocalPort, RemoteAddress, RemotePort |
  Format-Table LocalAddress, LocalPort, RemoteAddress, RemotePort, State, OwningProcess
```

4. 在 Wireshark 中应用 `tcp.port == 9000`，为两条连接分别记录 `tcp.stream` 编号。
5. 依次使用 `tcp.stream == N` 跟踪两组握手、数据与关闭报文。
6. 让客户端正常结束，确认系统连接表与抓包中的关闭方向相互对应。

### 预期现象

- 服务端方向的两条已连接记录都使用本地端口 9000。
- 两个客户端连接具有不同的本地临时端口。
- Wireshark 为它们分配不同的 Stream 编号。
- 每个 Stream 都维护各自的 Seq、Ack 与连接生命周期。
- 响应报文会交换源端口和目标端口。

若连接结束过快，可以在客户端发送后等待键盘输入，或让服务端在受控实验中暂停数秒。系统状态查询与抓包应尽量靠近同一时间窗口。

## 理解检查

1. 两条连接分别是 `10.0.0.8:51000 -> 10.0.0.2:443` 和 `10.0.0.8:51001 -> 10.0.0.2:443`。操作系统依据哪个字段区分它们？
2. 收到一条 `10.0.0.2:443 -> 10.0.0.8:51000` 的报文时，它属于哪条连接、哪个方向？
3. 服务端日志记录客户端为 `203.0.113.9:62001`，客户端日志记录本地端点为 `192.168.1.20:49152`。哪类路径设备可以同时解释这两条事实？
4. 显示过滤器 `tcp.port == 9000` 与 `tcp.dstport == 9000` 的覆盖方向有什么差别？

<details>
<summary>参考答案</summary>

1. 客户端源端口分别为 51000 和 51001，两条记录形成各自的完整四元组。
2. 它属于第一条连接，是服务端到客户端的响应方向。
3. 具有源地址和源端口转换能力的 NAT 设备；内外两侧的抓包点会看到不同端点。
4. `tcp.port` 同时匹配源或目标端口，覆盖双向；`tcp.dstport` 只覆盖目标端口符合条件的报文方向。

</details>

## 本章小结

- 源端口和目标端口都是 16 位网络字节序整数。
- IP 地址把报文送达主机，端口帮助主机定位 TCP 通信端点。
- 完整四元组让同一服务端端口承载许多独立连接。
- 监听 Socket 围绕本地端点接收新连接，已连接 Socket 还具有明确的远端端点。
- NAT、代理和负载均衡器可能改变不同抓包点观察到的四元组。
- `tcp.stream` 适合追踪一条连接的双向报文，定向过滤器适合研究单一方向。
